## Padrão de Permissões

### Convenção de Nomenclatura

O sistema usa o padrão `entidade.operacao` para permissões:

- **entidade**: Nome da entidade em minúsculas (ex: `usuario`, `evento`, `financeiro`)
- **operacao**: Operação CRUD (`create`, `read`, `update`, `delete`)

### Permissões por Operação

| Operação | Permissão | Exemplo |
|----------|-----------|---------|
| Criar | `entidade.create` | `usuario.create`, `evento.create` |
| Ler | `entidade.read` | `usuario.read`, `evento.read` |
| Atualizar | `entidade.update` | `usuario.update`, `evento.update` |
| Deletar | `entidade.delete` | `usuario.delete`, `evento.delete` |

### Métodos Protegidos

**Métodos CRUD padrão**:
- `create()` → `@RequirePermission('entidade.create')`
- `update()` → `@RequirePermission('entidade.update')`
- `delete()` → `@RequirePermission('entidade.delete')`
- `getById()` → `@RequirePermission('entidade.read')`
- `list()` → `@RequirePermission('entidade.read')`

**Métodos customizados**:
- `findBy*()` → `@RequirePermission('entidade.read')`
- Outros métodos de consulta → `@RequirePermission('entidade.read')`

## Exemplos de Uso

### Exemplo 1: Criar Usuário

```typescript
// Controller
const usuario = await usuarioService.create(dto);

// Fluxo:
// 1. Controller chama service.create()
// 2. Decorator @RequirePermission('usuario.create') intercepta
```

## Fluxo de Execução

### Fluxo Normal (com permissão)

```
1. Controller chama método do Application Service
   ↓
2. Decorator @RequirePermission intercepta chamada
   ↓
3. Decorator extrai userId do RequestContext
   ↓
4. Decorator resolve AuthorizationService do DI container
   ↓
5. AuthorizationService verifica permissão no banco de dados
   ↓
6. Se tiver permissão → executa método original
   ↓
7. Retorna resultado para controller
```

### Fluxo de Erro (sem permissão)

```
1. Controller chama método do Application Service
   ↓
2. Decorator @RequirePermission intercepta chamada
   ↓
3. Decorator extrai userId do RequestContext
   ↓
4. Decorator resolve AuthorizationService do DI container
   ↓
5. AuthorizationService verifica permissão no banco de dados
   ↓
6. Se NÃO tiver permissão → lança ForbiddenException
   ↓
7. errorHandler captura ForbiddenException
   ↓
8. Retorna resposta 403 com mensagem de erro
```

## Integração com Sistema Existente

### Dependências

- **T11.1 (Decorators de Autorização)**: Usa decorators `@RequirePermission`
- **T11.3 (Authorization Service)**: Decorators usam `AuthorizationService` para verificar permissões
- **T2.4 (RequestContext)**: Decorators extraem `userId` do `RequestContext`
- **T2.2 (ErrorHandler)**: `ForbiddenException` é tratada pelo `errorHandler`

### Ordem de Decorators

Quando múltiplos decorators são aplicados, a ordem é importante:

```typescript
@RequirePermission('usuario.create')  // 1. Verifica permissão primeiro
@Transactional()                      // 2. Depois inicia transação
async create(dto: CreateUsuarioDto): Promise<UsuarioResponseDto> {
  // ...
}
```

**Ordem recomendada**:
1. Decorators de autorização (`@RequirePermission`, `@RequireRole`)
2. Decorators de transação (`@Transactional`)
3. Método

## Testes

### Testes de Integração

Os testes de integração devem verificar:

1. **Com permissão**:
   - ✅ Método executa normalmente
   - ✅ Retorna resultado esperado
   - ✅ Não lança exceção

2. **Sem permissão**:
   - ✅ Método não executa
   - ✅ Lança `ForbiddenException`
   - ✅ Mensagem de erro apropriada

3. **Usuário não autenticado**:
   - ✅ Lança `UnauthorizedException` ou `ForbiddenException`
   - ✅ Mensagem de erro apropriada

### Exemplo de Teste

```typescript
describe('UsuarioApplicationService - Autorização', () => {
  it('deve lançar ForbiddenException se usuário não tiver permissão', async () => {
    // Arrange
    const userId = 1; // Usuário sem permissão
    mockAuthService.hasPermission.mockResolvedValue(false);

    // Act & Assert
    await expect(service.create(dto)).rejects.toThrow(ForbiddenException);
  });

  it('deve executar método se usuário tiver permissão', async () => {
    // Arrange
    const userId = 1; // Usuário com permissão
    mockAuthService.hasPermission.mockResolvedValue(true);

    // Act
    const result = await service.create(dto);

    // Assert
    expect(result).toBeDefined();
    expect(mockRepository.create).toHaveBeenCalled();
  });
});
```

## Considerações Importantes

### Performance

- Decorators executam verificação de permissão em **cada chamada** de método
- Para melhorar performance, implementar cache de permissões (T12.4)
- Verificações são feitas antes da execução do método, evitando processamento desnecessário

### Segurança

- **Nunca confiar apenas em autorização no frontend**: Decorators garantem autorização no backend
- **Verificar permissões antes de operações críticas**: Decorators fazem isso automaticamente
- **Logging**: Todas as tentativas de acesso sem permissão são logadas pelo `errorHandler`

### Manutenibilidade

- **Padrão consistente**: Todos os Application Services seguem o mesmo padrão
- **Fácil de adicionar**: Apenas adicionar decorator ao método
- **Documentação automática**: Decorators servem como documentação de permissões necessárias
