## Contexto Técnico

### Por que Políticas de Autorização?

Políticas permitem implementar regras de autorização complexas que vão além de simples verificação de permissões:

- **Regras baseadas em propriedades do recurso**: "Usuário só pode editar recursos que ele criou"
- **Regras multi-tenant**: "Usuário só pode acessar recursos do seu tenant"
- **Regras de negócio específicas**: Qualquer regra customizada que não seja apenas permissão/role

### Diferença entre Permissões e Políticas

- **Permissões**: Verificação simples se usuário tem permissão X
- **Políticas**: Verificação complexa baseada em contexto (recurso, usuário, propriedades)

**Exemplo**:
- Permissão: `usuario.update` → "Usuário tem permissão para atualizar usuários?"
- Política: `owner` → "Usuário é dono deste usuário específico?"

## Arquivos Criados

### 1. `src/core/authorization/IAuthorizationPolicy.ts`

Interface que define o contrato para políticas de autorização:

```typescript
export interface AuthorizationContext {
  userId: number;
  resourceId?: number;
  resource?: any;
  [key: string]: any;
}

export interface IAuthorizationPolicy {
  name: string;
  check(context: AuthorizationContext): Promise<boolean>;
}
```

**Características**:
- `AuthorizationContext`: Contexto flexível com informações do usuário e recurso
- `IAuthorizationPolicy`: Interface simples com método `check()`
- Extensível através de propriedades adicionais no contexto

### 2. `src/core/authorization/PolicyRegistry.ts`

Sistema de registro e resolução de políticas:

```typescript
export const PolicyRegistry = new PolicyRegistryClass();

// Registrar política
PolicyRegistry.register(new OwnerPolicy());

// Resolver política
const policy = PolicyRegistry.resolve('owner');
```

**Métodos**:
- `register(policy)`: Registra uma política
- `resolve(name)`: Resolve política por nome
- `has(name)`: Verifica se política está registrada
- `list()`: Lista todas as políticas registradas
- `unregister(name)`: Remove política do registro
- `clear()`: Limpa todas as políticas (útil para testes)

### 3. `src/core/authorization/policies/OwnerPolicy.ts`

Política que verifica se o usuário é dono do recurso:

```typescript
export class OwnerPolicy implements IAuthorizationPolicy {
  name = 'owner';

  async check(context: AuthorizationContext): Promise<boolean> {
    if (!context.resource || !context.resource.userId) {
      return false;
    }
    return context.resource.userId === context.userId;
  }
}
```

**Lógica**:
- Verifica se recurso existe
- Verifica se recurso possui propriedade `userId`
- Compara `resource.userId` com `context.userId`

### 4. `src/core/authorization/policies/SameTenantPolicy.ts`

Política que verifica se usuário e recurso pertencem ao mesmo tenant:

```typescript
export class SameTenantPolicy implements IAuthorizationPolicy {
  name = 'sameTenant';

  async check(context: AuthorizationContext): Promise<boolean> {
    if (!context.resource) return false;
    
    // Se não há tenantId, assumir que não há multi-tenancy
    if (!context.resource.tenantId || !context.tenantId) {
      return true;
    }
    
    return context.resource.tenantId === context.tenantId;
  }
}
```

**Lógica**:
- Verifica se recurso existe
- Se não há `tenantId`, assume que não há multi-tenancy (retorna `true`)
- Compara `resource.tenantId` com `context.tenantId`

### 5. `src/core/authorization/RequirePolicy.ts`

Decorator para aplicar políticas em métodos:

```typescript
export function RequirePolicy(
  policyName: string, 
  options?: RequirePolicyOptions
) {
  // ...
}
```

**Características**:
- Resolve política do `PolicyRegistry`
- Extrai `userId` do contexto
- Busca recurso automaticamente (se necessário)
- Cria `AuthorizationContext` com informações necessárias
- Chama `policy.check()` e lança `ForbiddenException` se não passar

**Opções**:
- `resourceIdParam`: Nome da propriedade que contém o ID do recurso
- `resourceParam`: Nome da propriedade que contém o recurso completo
- `getResource`: Função para buscar o recurso se não estiver disponível

### 6. `src/core/authorization/registerPolicies.ts`

Função para registrar políticas padrão:

```typescript
export function registerDefaultPolicies(): void {
  PolicyRegistry.register(new OwnerPolicy());
  PolicyRegistry.register(new SameTenantPolicy());
}
```

**Chamada**: Automática durante `initializeContainer()`

## Exemplos de Uso

### Exemplo 1: Usar OwnerPolicy em Application Service

```typescript
@Injectable()
export class EventoApplicationService {
  constructor(
    @Inject(TYPES.IEventoRepository) private repository: IEventoRepository
  ) {}

  @RequirePolicy('owner', {
    getResource: async (id: number) => await this.repository.findById(id)
  })
  async update(id: number, dto: UpdateEventoDto): Promise<EventoResponseDto> {
    // Método só será executado se usuário for dono do evento
    const evento = await this.repository.findById(id);
    // ...
  }
}
```

### Exemplo 5: Criar Política Customizada

```typescript
import { IAuthorizationPolicy, AuthorizationContext } from '../IAuthorizationPolicy';
import { PolicyRegistry } from '../PolicyRegistry';

export class CustomPolicy implements IAuthorizationPolicy {
  name = 'custom';

  async check(context: AuthorizationContext): Promise<boolean> {
    // Implementar lógica customizada
    if (!context.resource) return false;
    
    // Exemplo: verificar se recurso está ativo
    if (context.resource.status !== 'ACTIVE') {
      return false;
    }
    
    // Exemplo: verificar se usuário tem role específica para este tipo de recurso
    if (context.resource.type === 'PREMIUM' && context.userRole !== 'PREMIUM_USER') {
      return false;
    }
    
    return true;
  }
}

// Registrar política
PolicyRegistry.register(new CustomPolicy());
```

## Fluxo de Execução

### Fluxo Normal (política satisfeita)

```
1. Método decorado é chamado
   ↓
2. Decorator @RequirePolicy intercepta
   ↓
3. Resolve política do PolicyRegistry
   ↓
4. Extrai userId do RequestContext
   ↓
5. Busca recurso (se necessário via getResource)
   ↓
6. Cria AuthorizationContext
   ↓
7. Chama policy.check(context)
   ↓
8. Se política satisfeita → executa método original
   ↓
9. Retorna resultado
```

### Fluxo de Erro (política não satisfeita)

```
1. Método decorado é chamado
   ↓
2. Decorator @RequirePolicy intercepta
   ↓
3. Resolve política do PolicyRegistry
   ↓
4. Extrai userId do RequestContext
   ↓
5. Busca recurso (se necessário)
   ↓
6. Cria AuthorizationContext
   ↓
7. Chama policy.check(context)
   ↓
8. Se política NÃO satisfeita → lança ForbiddenException
   ↓
9. errorHandler captura ForbiddenException
   ↓
10. Retorna resposta 403
```

## Políticas Implementadas

### OwnerPolicy

**Nome**: `owner`

**Descrição**: Verifica se o usuário é dono do recurso sendo acessado.

**Lógica**:
- Verifica se `context.resource` existe
- Verifica se `context.resource.userId` ou `context.resource.usuarioId` existe
- Compara propriedade do recurso com `context.userId`
- Suporta múltiplas convenções: `userId` (padrão) e `usuarioId` (alguns modelos)

**Uso**:
```typescript
@RequirePolicy('owner', {
  getResource: async (id: number) => await this.repository.findById(id)
})
async update(id: number, dto: UpdateDto): Promise<ResponseDto> {
  // ...
}
```

**Casos de Uso**:
- Usuário só pode editar seus próprios eventos
- Usuário só pode deletar seus próprios lembretes
- Usuário só pode atualizar seus próprios registros financeiros

### SameTenantPolicy

**Nome**: `sameTenant`

**Descrição**: Verifica se usuário e recurso pertencem ao mesmo tenant.

**Lógica**:
- Verifica se `context.resource` existe
- Se não há `tenantId` em recurso ou usuário, assume que não há multi-tenancy (retorna `true`)
- Compara `context.resource.tenantId === context.tenantId`

**Uso**:
```typescript
@RequirePolicy('sameTenant', {
  getResource: async (id: number) => await this.repository.findById(id)
})
async delete(id: number): Promise<boolean> {
  // ...
}
```

**Casos de Uso**:
- Garantir isolamento de dados entre tenants
- Prevenir acesso cross-tenant
- Compliance em sistemas multi-tenant

**Nota**: Esta política assume que o sistema implementa multi-tenancy completo. Se não implementado, a política retorna `true` para não bloquear acesso.

## Considerações Importantes

### Performance

- Políticas executam verificação em **cada chamada** de método
- Se `getResource` for fornecido, busca adicional ao banco de dados
- Para melhorar performance, considerar cache de recursos ou passar recurso diretamente

### Segurança

- **Sempre validar**: Políticas devem validar todos os casos de erro
- **Não confiar em dados do cliente**: Sempre buscar recurso do banco de dados
- **Logging**: Considerar logar tentativas de acesso bloqueadas por políticas

### Extensibilidade

- Sistema permite criar políticas customizadas facilmente
- Políticas podem acessar qualquer informação do `AuthorizationContext`
- Políticas podem usar `AuthorizationService` se necessário

## Limitações e Considerações

### Busca de Recurso

O decorator tenta obter o recurso automaticamente, mas pode não funcionar em todos os casos:

- **Solução**: Sempre fornecer `getResource` quando possível
- **Alternativa**: Passar recurso como argumento e usar `resourceParam`

### Multi-Tenancy

`SameTenantPolicy` assume que o sistema implementa multi-tenancy completo. Se não implementado:

- Política retorna `true` para não bloquear acesso
- Quando multi-tenancy for implementado, política funcionará automaticamente

### Ordem de Verificação

Quando múltiplas políticas são aplicadas, todas devem ser satisfeitas:

```typescript
// Todas as políticas devem passar
@RequirePolicy('owner')
@RequirePolicy('sameTenant')
async update(id: number, dto: UpdateDto): Promise<ResponseDto> {
  // ...
}
```
