## Contexto Técnico

### Antes da Refatoração

**Problemas identificados**:
- Rotas protegidas apenas com `authMiddleware` (autenticação, não autorização)
- Verificações manuais de permissões em alguns controllers
- Inconsistência na aplicação de autorização
- Falta de documentação clara sobre permissões necessárias

**Exemplo de código antigo**:
```typescript
// Controller com verificação manual
async update(req: Request, res: Response) {
  const userId = req.userId;
  const eventoExistente = await this.eventoService.getById(id);
  
  if (eventoExistente.usuarioId !== Number(userId)) {
    throw new ForbiddenException('Você não tem permissão para atualizar este evento');
  }
  
  // ...
}
```

### Depois da Refatoração

**Solução implementada**:
- Middleware de autorização aplicado em todas as rotas
- Verificações manuais removidas dos controllers
- Autorização dupla: middleware nas rotas + decorators nos Application Services
- Documentação clara de permissões

**Exemplo de código novo**:
```typescript
// Rota com middleware de autorização
router.put(
  '/:id',
  requirePermission('evento.update'),
  validateDtoUpdate(UpdateEventoDto),
  asyncHandler(async (req, res) => {
    await getEventoController().update(req, res);
  })
);

// Controller simplificado (sem verificações manuais)
async update(req: Request, res: Response) {
  const { id } = req.params;
  const dto = req.body as UpdateEventoDto;
  const updatedEvento = await this.eventoService.update(id, dto);
  return res.json(updatedEvento);
}
```

## Padrão de Aplicação

### Estrutura Padrão de Rota

```typescript
import { requirePermission } from '../middleware/authorization';
import { asyncHandler } from '../middleware/errorHandler';

/**
 * [Método] /api/[recurso]
 * 
 * [Descrição da rota]
 * 
 * Permissão necessária: [permissao]
 */
router.[metodo](
  '/[rota]',
  requirePermission('[permissao]'),
  [validateDto se necessário],
  asyncHandler(async (req, res) => {
    await getController().[metodo](req, res);
  })
);
```

### Ordem dos Middlewares

A ordem correta dos middlewares é:

1. **`authMiddleware`** (aplicado no `routes/index.ts` para todas as rotas protegidas)
2. **`requirePermission`** (middleware de autorização específico da rota)
3. **`validateDto`** (validação de dados, se necessário)
4. **`asyncHandler`** (wrapper para tratamento de erros assíncronos)
5. **Controller handler**

**Exemplo**:
```typescript
// routes/index.ts
router.use('/eventos', authMiddleware, eventoRoutes);

// routes/evento.routes.ts
router.post(
  '/',
  requirePermission('evento.create'),  // 1. Autorização
  validateDto(CreateEventoDto),         // 2. Validação
  asyncHandler(async (req, res) => {   // 3. Handler
    await getEventoController().create(req, res);
  })
);
```

## Remoção de Verificações Manuais

### Antes

**EventoController.update()**:
```typescript
async update(req: Request, res: Response) {
  const userId = req.userId;
  if (!userId) {
    throw new NotFoundException('Usuário');
  }

  const { id } = req.params;
  const dto = req.body as UpdateEventoDto;
  
  // Verificação manual de permissão
  const eventoExistente = await this.eventoService.getById(id);
  if (!eventoExistente) {
    throw new NotFoundException('Evento', id);
  }

  if (eventoExistente.usuarioId !== Number(userId)) {
    throw new ForbiddenException('Você não tem permissão para atualizar este evento');
  }

  const updatedEvento = await this.eventoService.update(id, dto);
  return res.json(updatedEvento);
}
```

### Depois

**EventoController.update()**:
```typescript
async update(req: Request, res: Response) {
  const { id } = req.params;
  const dto = req.body as UpdateEventoDto;
  
  // Autorização é feita pelo middleware e Application Service
  const updatedEvento = await this.eventoService.update(id, dto);
  return res.json(updatedEvento);
}
```

**Benefícios**:
- Código mais limpo e simples
- Responsabilidade única: controller apenas delega para Application Service
- Autorização centralizada em middleware e decorators
- Mais fácil de manter e testar

## Camadas de Autorização

O sistema agora possui **duas camadas de autorização**:

### 1. Middleware nas Rotas (Camada HTTP)

**Responsabilidade**: Verificar permissão antes de chegar ao controller

**Vantagens**:
- Falha rápida: bloqueia requisição antes de processar
- Documentação clara: permissões visíveis nas rotas
- Consistência: todas as rotas seguem o mesmo padrão

**Exemplo**:
```typescript
router.put(
  '/:id',
  requirePermission('evento.update'),
  asyncHandler(async (req, res) => {
    // ...
  })
);
```

### 2. Decorators nos Application Services (Camada de Negócio)

**Responsabilidade**: Verificar permissão antes de executar lógica de negócio

**Vantagens**:
- Proteção mesmo se middleware for bypassado
- Flexibilidade: pode usar políticas customizadas (`@RequirePolicy`)
- Testabilidade: fácil de testar isoladamente

**Exemplo**:
```typescript
@RequirePermission('evento.update')
async update(id: number, dto: UpdateEventoDto): Promise<EventoResponseDto> {
  // ...
}
```

### Por que Duas Camadas?

- **Defesa em profundidade**: Se uma camada falhar, a outra protege
- **Flexibilidade**: Middleware para regras simples, decorators para regras complexas
- **Clareza**: Documentação explícita nas rotas

## Fluxo de Autorização

### Fluxo Normal (com permissão)

```
1. Requisição HTTP chega
   ↓
2. authMiddleware verifica autenticação (JWT)
   ↓
3. requirePermission verifica permissão (middleware)
   ↓
4. Controller recebe requisição
   ↓
5. Application Service (com @RequirePermission) verifica permissão novamente
   ↓
6. Método executa
   ↓
7. Resposta retornada
```

### Fluxo de Erro (sem permissão)

```
1. Requisição HTTP chega
   ↓
2. authMiddleware verifica autenticação (JWT)
   ↓
3. requirePermission verifica permissão (middleware)
   ↓
4. Se não tiver permissão → ForbiddenException (403)
   ↓
5. errorHandler captura exceção
   ↓
6. Resposta 403 retornada
```

## Considerações Importantes

### Performance

- Middleware de autorização executa **antes** do controller
- Se usuário não tiver permissão, requisição é bloqueada cedo
- Queries de autorização são otimizadas pelo `AuthorizationService`

### Segurança

- **Dupla proteção**: Middleware + Decorators
- **Falha segura**: Se middleware falhar, decorator protege
- **Sem bypass**: Não há como contornar autorização facilmente

### Manutenibilidade

- **Código limpo**: Controllers simplificados
- **Documentação clara**: Permissões visíveis nas rotas
- **Padrão consistente**: Todas as rotas seguem mesmo padrão
