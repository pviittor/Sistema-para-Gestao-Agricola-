## Ordem de Execução dos Decorators

A ordem dos decorators importa. A ordem correta é:

1. **`@RequirePermission`** - Verifica autorização primeiro
2. **`@Transactional`** - Inicia transação (se aplicável)
3. **`@Auditable`** - Registra auditoria após operação

**Exemplo**:
```typescript
@RequirePermission('evento.create')  // 1. Autorização
@Transactional()                      // 2. Transação
@Auditable('Evento')                 // 3. Auditoria
async create(dto: CreateEventoDto): Promise<EventoResponseDto> {
  // Método executado
}
```

**Motivo**:
- Autorização deve ser verificada antes de qualquer operação
- Transação deve envolver a operação e a auditoria
- Auditoria deve registrar após a operação ser concluída

## Validação

### Como Validar

1. **Executar operações**:
   - Criar usuário
   - Atualizar usuário
   - Excluir usuário
   - Criar evento
   - Atualizar evento
   - Excluir evento

2. **Verificar logs no banco**:
   ```sql
   SELECT * FROM audit_logs 
   WHERE entity IN ('Usuario', 'Evento') 
   ORDER BY timestamp DESC 
   LIMIT 10;
   ```

3. **Validar campos**:
   - ✅ userId está correto
   - ✅ action está correto (CREATE, UPDATE, DELETE)
   - ✅ entity está correto
   - ✅ entityId está correto
   - ✅ changes contém dados corretos
   - ✅ ip e userAgent estão presentes (se Request disponível)
   - ✅ timestamp está correto

### Testes Manuais

**Teste 1: Criar Usuário**
```bash
POST /api/usuarios
{
  "nome": "João Silva",
  "email": "joao@example.com",
  "username": "joao.silva",
  "senha": "senha123"
}
```

**Verificar log**:
- Deve ter action: CREATE
- Deve ter entity: Usuario
- Deve ter changes.after com dados do usuário

**Teste 2: Atualizar Usuário**
```bash
PUT /api/usuarios/123
{
  "nome": "João Silva Atualizado"
}
```

**Verificar log**:
- Deve ter action: UPDATE
- Deve ter changes.before com estado anterior
- Deve ter changes.after com estado novo
- Deve ter changes.changes com apenas mudanças

**Teste 3: Excluir Evento**
```bash
DELETE /api/eventos/456
```

**Verificar log**:
- Deve ter action: DELETE
- Deve ter changes.before com dados do evento excluído

## Considerações Importantes

### Performance

- **Overhead mínimo**: Decorator adiciona pouco overhead
- **Assíncrono**: Não bloqueia operações
- **Não crítico**: Erros não interrompem fluxo principal

### Segurança

- **Dados sensíveis**: Sanitizados automaticamente pelo AuditService
- **IP e UserAgent**: Capturados automaticamente quando Request disponível
- **Integridade**: Logs não são modificáveis após criação

### Manutenção

- **Código limpo**: Decorator mantém código simples
- **Fácil de aplicar**: Basta adicionar `@Auditable('Entity')`
- **Consistente**: Mesmo padrão em todos os métodos
