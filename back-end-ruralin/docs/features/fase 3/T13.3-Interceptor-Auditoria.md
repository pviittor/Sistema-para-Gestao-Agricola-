# T13.3 - Interceptor de Auditoria

## Resumo Executivo

Criação do decorator `@Auditable` para aplicar auditoria automática em métodos de Application Services. O interceptor captura automaticamente o estado antes (para UPDATE/DELETE), executa o método e registra auditoria, reduzindo código duplicado e garantindo que todas as operações sejam auditadas.

## Contexto Técnico

### Por que Interceptor de Auditoria?

**Problemas sem interceptor**:
- Código duplicado em cada método
- Fácil esquecer de adicionar auditoria
- Inconsistência na captura de estado antes
- Dificuldade de manutenção

**Benefícios com interceptor**:
- Código declarativo e simples
- Auditoria automática e consistente
- Redução de código duplicado
- Fácil de aplicar em novos métodos

**Casos de uso**:
- Aplicar em métodos create, update, delete
- Capturar estado antes automaticamente
- Registrar auditoria após operação
- Integrar com Request para contexto completo

## Funcionalidades Implementadas

### 1. Decorator @Auditable

Aplica auditoria automática em métodos.

**Sintaxe básica**:
```typescript
@Auditable('Usuario')
async create(dto: CreateUsuarioDto): Promise<UsuarioResponseDto> {
  // Auditoria registrada automaticamente após criação
}
```

**Sintaxe com opções**:
```typescript
@Auditable({
  entityName: 'Usuario',
  repositoryFindMethod: 'findById',
  idProperty: 'id'
})
async update(id: number, dto: UpdateUsuarioDto): Promise<UsuarioResponseDto> {
  // Estado antes capturado automaticamente
  // Auditoria registrada automaticamente após atualização
}
```

### 2. Detecção Automática de Operação

O decorator detecta automaticamente o tipo de operação pelo nome do método:

- `create` → Registra após criação
- `update` → Captura estado antes, executa, registra mudanças
- `delete` → Captura estado antes, executa, registra exclusão

**Exemplo**:
```typescript
class UsuarioApplicationService {
  @Auditable('Usuario')
  async create(dto: CreateUsuarioDto) {
    // Detectado como CREATE
  }

  @Auditable('Usuario')
  async update(id: number, dto: UpdateUsuarioDto) {
    // Detectado como UPDATE
  }

  @Auditable('Usuario')
  async delete(id: number) {
    // Detectado como DELETE
  }
}
```

### 3. Captura de Estado Antes

Para operações UPDATE e DELETE, o decorator captura automaticamente o estado antes da operação.

**Como funciona**:
1. Identifica o ID dos argumentos
2. Busca estado atual usando o repositório
3. Executa o método original
4. Registra auditoria com estado antes e depois

**Exemplo**:
```typescript
@Auditable('Usuario')
async update(id: number, dto: UpdateUsuarioDto) {
  // Estado antes é capturado automaticamente:
  // const before = await this.repository.findById(id);
  
  // Método é executado
  const updated = await this.repository.update(id, dto);
  
  // Auditoria registrada automaticamente:
  // await auditService.logUpdate('Usuario', id, before, updated);
  
  return updated;
}
```

### 4. Integração com Request

O decorator detecta automaticamente o Request nos argumentos e o passa para o AuditService.

**Exemplo**:
```typescript
@Auditable('Usuario')
async create(dto: CreateUsuarioDto, req?: Request) {
  // Request é detectado automaticamente e passado para AuditService
  // IP e UserAgent são capturados automaticamente
}
```

### 5. Opções Customizadas

O decorator suporta várias opções para casos especiais:

**Opções disponíveis**:
- `entityName`: Nome da entidade (se não fornecido, é inferido)
- `repositoryFindMethod`: Método do repositório para buscar estado antes
- `idProperty`: Propriedade que contém o ID no resultado
- `getIdFromArgs`: Função customizada para obter ID
- `getBeforeState`: Função customizada para obter estado antes

**Exemplo com opções**:
```typescript
@Auditable({
  entityName: 'Usuario',
  repositoryFindMethod: 'findByPk',
  getIdFromArgs: (dto) => dto.usuarioId,
  getBeforeState: async (service, id) => {
    // Lógica customizada para buscar estado antes
    return await service.repository.findWithRelations(id);
  }
})
async update(dto: UpdateUsuarioDto) {
  // ...
}
```

## Exemplos de Uso

### Exemplo 1: Uso Básico

```typescript
import { Auditable } from '../../core/audit';

export class UsuarioApplicationService {
  @Auditable('Usuario')
  async create(dto: CreateUsuarioDto): Promise<UsuarioResponseDto> {
    const entity = await this.mapper.toEntity(dto);
    const created = await this.repository.create(entity);
    return this.mapper.toDto(created);
  }

  @Auditable('Usuario')
  async update(id: number, dto: UpdateUsuarioDto): Promise<UsuarioResponseDto> {
    const existing = await this.repository.findById(id);
    if (!existing) {
      throw new NotFoundException('Usuário', id);
    }

    const entity = await this.mapper.toEntity(dto);
    const updated = await this.repository.update(id, entity);
    return this.mapper.toDto(updated);
  }

  @Auditable('Usuario')
  async delete(id: number): Promise<boolean> {
    return await this.repository.delete(id);
  }
}
```

### Exemplo 2: Com Request

```typescript
import { Request } from 'express';
import { Auditable } from '../../core/audit';

export class UsuarioApplicationService {

}
```

### Exemplo 3: Com Opções Customizadas

```typescript
import { Auditable } from '../../core/audit';

export class EventoApplicationService {
  @Auditable({
    entityName: 'Evento',
    repositoryFindMethod: 'findById',
    getBeforeState: async (service, id) => {
      // Buscar com relacionamentos para auditoria completa
      return await service.repository.findOne({
        where: { id },
        include: ['local', 'usuario']
      });
    }
  })
  async update(id: number, dto: UpdateEventoDto): Promise<EventoResponseDto> {
    // Estado antes incluirá relacionamentos
    const entity = await this.mapper.toEntity(dto);
    const updated = await this.repository.update(id, entity);
    return this.mapper.toDto(updated);
  }
}
```

## Fluxo de Execução

### CREATE

1. Método `create` é chamado
2. Decorator intercepta a chamada
3. Método original é executado
4. Resultado é obtido (com ID)
5. `auditService.logCreate()` é chamado automaticamente
6. Resultado é retornado

### UPDATE

1. Método `update` é chamado
2. Decorator intercepta a chamada
3. ID é extraído dos argumentos
4. Estado antes é buscado via repositório
5. Método original é executado
6. Resultado é obtido
7. `auditService.logUpdate()` é chamado automaticamente
8. Resultado é retornado

### DELETE

1. Método `delete` é chamado
2. Decorator intercepta a chamada
3. ID é extraído dos argumentos
4. Estado antes é buscado via repositório
5. Método original é executado
6. `auditService.logDelete()` é chamado automaticamente
7. Resultado é retornado

## Integração com Sistema Existente

### Requisitos

**Dependências**:
- `AuditService` deve estar registrado no DI container
- Application Service deve ter propriedade `repository` (ou usar opção customizada)

**Estrutura esperada**:
```typescript
export class UsuarioApplicationService {
  // Propriedade 'repository' é usada para buscar estado antes
  constructor(
    @Inject(TYPES.IUsuarioRepository)
    private repository: IUsuarioRepository
  ) {}
}
```

### Compatibilidade

**Funciona com**:
- ✅ `@RequirePermission` (pode ser usado junto)
- ✅ `@Transactional` (pode ser usado junto)
- ✅ `@RequirePolicy` (pode ser usado junto)

**Ordem de execução**:
1. `@RequirePermission` / `@RequirePolicy` (autorização)
2. `@Transactional` (transação)
3. `@Auditable` (auditoria)

## Tratamento de Erros

### Estratégia

**Não lança erros**: O decorator não lança erros para não interromper o fluxo principal.

**Loga erros**: Erros são logados no console (futuro: integrar com Logger).

**Exemplo**:
```typescript
@Auditable('Usuario')
async create(dto: CreateUsuarioDto) {
  // Se auditoria falhar, método ainda retorna resultado
  // Erro é logado mas não interrompe operação
}
```

**Motivo**:
- Auditoria não deve interromper operações críticas
- Sistema pode continuar funcionando mesmo com problemas de auditoria
- Erros são tratados internamente pelo AuditService

## Considerações Importantes

### Performance

- **Overhead mínimo**: Interceptação adiciona pouco overhead
- **Assíncrono**: Todas as operações são assíncronas
- **Não bloqueante**: Erros não interrompem fluxo principal

### Limitações

- **Requisito de repositório**: Service deve ter propriedade `repository` (ou usar opção customizada)
- **Detecção de operação**: Baseada no nome do método (create, update, delete)
- **ID do resultado**: Para CREATE, assume que resultado tem propriedade `id`

### Boas Práticas

1. **Sempre especificar entityName**: Evita problemas com inferência
2. **Usar opções customizadas quando necessário**: Para casos especiais
3. **Passar Request quando disponível**: Para capturar IP e UserAgent
4. **Testar com diferentes cenários**: Garantir que funciona corretamente
