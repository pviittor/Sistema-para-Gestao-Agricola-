## Contexto Técnico

### Problema Identificado

**Antes das otimizações**:
- Cada verificação de permissão executava múltiplas queries ao banco
- Mesmas permissões eram verificadas repetidamente sem cache
- Performance degradava com aumento de requisições
- Queries não otimizadas (múltiplas queries separadas)

**Exemplo de queries antes**:
```sql
-- hasPermission executava:
SELECT * FROM usuarios WHERE id = ?;           -- Query 1
SELECT * FROM permissoes WHERE nome = ?;       -- Query 2
SELECT * FROM usuario_has_role WHERE usuarioId = ?;  -- Query 3
SELECT * FROM role_has_permissao WHERE roleId IN (...) AND permissaoId = ?;  -- Query 4
```

### Solução Implementada

**Depois das otimizações**:
- Cache de permissões e roles reduz queries ao banco
- Queries otimizadas usando cache de dados frequentes
- Invalidação automática quando dados mudam
- Base preparada para migração para Redis

**Exemplo de queries depois**:
```sql
-- Primeira chamada (cache miss):
SELECT * FROM permissoes WHERE nome = ?;       -- Query 1 (cacheado)
SELECT * FROM usuario_has_role WHERE usuarioId = ?;  -- Query 2 (cacheado)
SELECT * FROM role_has_permissao WHERE roleId IN (...) AND permissaoId = ?;  -- Query 3

-- Chamadas subsequentes (cache hit):
-- Nenhuma query ao banco! Resposta instantânea do cache
```

## Arquivos Criados

### 1. `src/core/cache/ICacheService.ts`

Interface para serviços de cache, permitindo diferentes implementações.

**Características**:
- Interface genérica para cache
- Suporta TTL (Time To Live)
- Métodos: `get`, `set`, `delete`, `clear`, `exists`, `deleteByPattern`
- Preparada para Redis (T15.1)

**Métodos**:
```typescript
interface ICacheService {
  get<T>(key: string): Promise<T | null>;
  set(key: string, value: any, ttl?: number): Promise<void>;
  delete(key: string): Promise<void>;
  clear(): Promise<void>;
  exists(key: string): Promise<boolean>;
  deleteByPattern(pattern: string): Promise<number>;
}
```

### 2. `src/infrastructure/cache/InMemoryCacheService.ts`

Implementação de cache em memória para desenvolvimento.

**Características**:
- Cache em memória usando `Map`
- Suporta TTL com limpeza automática
- Thread-safe para Node.js
- Preparado para substituição por Redis

**Funcionalidades**:
- Armazenamento em memória
- Limpeza automática de entradas expiradas (a cada 1 minuto)
- Suporte a padrões para invalidação em massa
- Estatísticas do cache (útil para debugging)

## Estratégia de Cache

### Chaves de Cache

**Padrão de nomenclatura**:
- Permissões: `auth:permission:{userId}:{permission}`
- Roles: `auth:role:{userId}:{role}`
- Roles do usuário: `auth:user:roles:{userId}`
- Permissões do usuário: `auth:user:permissions:{userId}`
- Permissão por nome: `permissao:{nome}`
- Role por nome: `role:{nome}`

**Exemplos**:
```
auth:permission:1:usuario.create
auth:role:1:ADMIN
auth:user:roles:1
permissao:usuario.create
role:ADMIN
```

### TTL (Time To Live)

**Configurações**:
- **Permissões e Roles do usuário**: 1 hora (3600 segundos)
- **Permissões e Roles por nome**: 24 horas (86400 segundos)

**Justificativa**:
- Permissões e roles do usuário mudam com frequência média
- Permissões e roles por nome raramente mudam
- Balanceamento entre performance e consistência

### Estratégia de Cache

**Cache-Aside Pattern**:
1. Verificar cache primeiro
2. Se cache hit, retornar valor
3. Se cache miss, buscar do banco
4. Armazenar no cache para próximas chamadas

**Fluxo**:
```
Requisição → Verificar Cache → Cache Hit? → Sim → Retornar
                                    ↓ Não
                              Buscar do Banco → Armazenar no Cache → Retornar
```

## Otimizações de Queries

### Antes

**hasPermission** executava:
1. Query para buscar usuário
2. Query para buscar permissão por nome
3. Query para buscar roles do usuário
4. Query para buscar permissões das roles

**Total**: 4 queries por verificação

### Depois

**hasPermission** com cache:
1. Verificar cache de permissão (sem query)
2. Se cache miss, buscar permissão (1 query, cacheada)
3. Verificar cache de roles do usuário (sem query)
4. Se cache miss, buscar roles (1 query, cacheada)
5. Query otimizada para verificar permissão (1 query)

**Total**: 1-3 queries na primeira chamada, 0 queries nas subsequentes

### Otimizações Específicas

1. **Uso de `findOne` em vez de `findAll`**:
   ```typescript
   // Antes
   const rolePermissoes = await RoleHasPermissao.findAll({...});
   return rolePermissoes.length > 0;

   // Depois
   const rolePermissao = await RoleHasPermissao.findOne({...});
   return rolePermissao !== null;
   ```

2. **Cache de dados frequentes**:
   - Permissões por nome (raramente mudam)
   - Roles por nome (raramente mudam)
   - Roles do usuário (mudam com frequência média)

3. **Reutilização de cache**:
   - `hasRole` reutiliza cache de roles do usuário
   - `hasAnyRole` e `hasAllRoles` reutilizam cache de roles

## Sistema de Invalidação

### Métodos de Invalidação

#### 1. `invalidateUserCache(userId)`

Invalida todo o cache relacionado a um usuário específico.

**Quando usar**:
- Quando roles do usuário mudarem
- Quando permissões do usuário mudarem
- Quando usuário for deletado

**Exemplo**:
```typescript
// Após atribuir role a usuário
await usuarioHasRoleService.create(usuarioId, roleId);
await authService.invalidateUserCache(usuarioId);
```

#### 2. `invalidatePermissionCache(permissionName)`

Invalida cache de uma permissão específica e todas as verificações que a usam.

**Quando usar**:
- Quando permissão for modificada
- Quando permissão for deletada

**Exemplo**:
```typescript
// Após modificar permissão
await permissaoService.update(permissaoId, dto);
await authService.invalidatePermissionCache(dto.nome);
```

#### 3. `invalidateRoleCache(roleName)`

Invalida cache de uma role específica e todas as verificações que a usam.

**Quando usar**:
- Quando role for modificada
- Quando role for deletada
- Quando permissões da role mudarem

**Exemplo**:
```typescript
// Após modificar role
await roleService.update(roleId, dto);
await authService.invalidateRoleCache(dto.nome);
```

#### 4. `invalidateAllCache()`

Limpa todo o cache de autorização.

**Quando usar**:
- Em caso de mudanças significativas
- Para limpeza completa
- Em caso de problemas de consistência

**Exemplo**:
```typescript
// Após migração de dados
await authService.invalidateAllCache();
```

### Integração com Application Services

**Recomendação**: Chamar métodos de invalidação nos Application Services quando dados mudarem.

**Exemplo**:
```typescript
@Injectable()
export class UsuarioHasRoleApplicationService {
  constructor(
    @Inject(TYPES.IAuthorizationService) private authService: IAuthorizationService
  ) {}

  async create(usuarioId: number, roleId: number): Promise<void> {
    // Criar associação
    await this.repository.create({ usuarioId, roleId });
    
    // Invalidar cache do usuário
    await this.authService.invalidateUserCache(usuarioId);
  }
}
```

## Performance

### Melhorias Esperadas

**Redução de Queries**:
- **Antes**: 4 queries por verificação de permissão
- **Depois**: 0 queries após cache hit (até 3 queries no cache miss)

**Redução de Latência**:
- **Antes**: ~50-100ms por verificação (dependendo do banco)
- **Depois**: ~1-5ms após cache hit (memória)

**Throughput**:
- **Antes**: Limitado por queries ao banco
- **Depois**: Limitado apenas por processamento em memória

### Métricas de Cache

**Taxa de Cache Hit**:
- Esperada: 80-95% em produção
- Depende de padrão de uso

**Redução de Carga no Banco**:
- Esperada: 80-95% de redução em queries de autorização
- Significativa melhoria em alta concorrência

## Migração para Redis

### Preparação

A implementação atual usa `InMemoryCacheService` que pode ser facilmente substituída por `RedisCacheService` (T15.1).

**Vantagens do Redis**:
- Cache distribuído (múltiplas instâncias)
- Persistência opcional
- Melhor para produção
- Suporte a clusters

**Migração**:
1. Implementar `RedisCacheService` (T15.1)
2. Alterar registro no DI container:
   ```typescript
   // De:
   container.registerSingleton(TYPES.ICacheService, InMemoryCacheService);
   
   // Para:
   container.registerSingleton(TYPES.ICacheService, RedisCacheService);
   ```
3. Nenhuma mudança necessária no `AuthorizationService` (usa interface)

## Considerações Importantes

### Consistência

- Cache pode ficar desatualizado se invalidação não for chamada
- **Solução**: Sempre chamar métodos de invalidação quando dados mudarem

### Memória

- Cache in-memory cresce com número de usuários
- **Solução**: Migrar para Redis em produção (T15.1)

### Thread Safety

- `InMemoryCacheService` é thread-safe para Node.js (single-threaded)
- Redis é thread-safe por design
