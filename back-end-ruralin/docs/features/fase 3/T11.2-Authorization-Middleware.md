# T11.2 - Authorization Middleware

## Resumo Executivo

Implementação de middleware de autorização para verificação de permissões e roles em nível de rota. Este middleware complementa os decorators de autorização (`@RequirePermission`, `@RequireRole`) permitindo proteção de rotas que não usam Application Services ou quando é necessário proteger rotas diretamente.

## Decisões de Implementação

### Abordagem Escolhida

**Middleware Factory Pattern**:
- Usa funções factory que retornam middlewares do Express
- Permite configuração flexível por rota
- Reutilizável e fácil de testar

**Sistema de Exceções Centralizado**:
- Usa `UnauthorizedException` para erros de autenticação (401)
- Usa `ForbiddenException` para erros de autorização (403)
- Todas as exceções são passadas para o `errorHandler`
- Formatação padronizada de respostas de erro

**Integração com DI Container**:
- Resolve `IAuthorizationService` do container em cada requisição
- Não mantém estado entre requisições
- Facilita testes com mocks

**Verificações em Paralelo**:
- `requireAnyPermission` e `requireAllPermissions` usam `Promise.all()`
- Melhora performance quando há múltiplas verificações
- Reduz tempo de resposta

## Contexto Técnico

### Por que Middleware de Autorização?

O middleware de autorização complementa os decorators de autorização implementados na tarefa T11.1:

- **Decorators**: Protegem métodos de Application Services automaticamente
- **Middleware**: Protege rotas diretamente, útil para:
  - Rotas que não usam Application Services
  - Proteção adicional em nível de rota
  - Flexibilidade na organização de autorização

### Integração com Sistema Existente

- **authMiddleware**: O middleware de autorização depende do `authMiddleware` que define `req.userId`
- **AuthorizationService**: Usa `IAuthorizationService` resolvido do DI container
- **errorHandler**: Lança `ForbiddenException` que é tratada pelo `errorHandler`
- **RequestContext**: Pode ser usado para obter informações adicionais do contexto

## Arquivos Criados

### 1. `src/middleware/authorization.ts`

Middleware de autorização com as seguintes funções:

#### `requirePermission(permission: string)`

Middleware factory que verifica se o usuário tem uma permissão específica.

```typescript
export const requirePermission = (permission: string) => {
  return async (req: Request, res: Response, next: NextFunction): Promise<void> => {
    // Verifica autenticação
    // Resolve AuthorizationService
    // Verifica permissão
    // Lança ForbiddenException se não tiver permissão
    // Chama next() se tiver permissão
  };
};
```

**Características**:
- Verifica se usuário está autenticado (`req.userId`)
- Resolve `IAuthorizationService` do DI container
- Verifica permissão usando `authService.hasPermission()`
- Lança `UnauthorizedException` (401) se não estiver autenticado
- Lança `ForbiddenException` (403) se não tiver permissão
- Todas as exceções são tratadas pelo `errorHandler`

#### `requireRole(role: string | string[])`

Middleware factory que verifica se o usuário tem uma role específica (ou pelo menos uma das roles, se array).

```typescript
export const requireRole = (role: string | string[]) => {
  return async (req: Request, res: Response, next: NextFunction): Promise<void> => {
    // Verifica autenticação
    // Resolve AuthorizationService
    // Normaliza role para array
    // Verifica role usando hasAnyRole (OR)
    // Lança ForbiddenException se não tiver role
    // Chama next() se tiver role
  };
};
```

**Características**:
- Suporta role única ou array de roles (OR)
- Usa `authService.hasAnyRole()` para verificação
- Mensagem de erro inclui todas as roles necessárias

#### `requireAnyPermission(permissions: string[])`

Middleware factory que verifica se o usuário tem pelo menos uma das permissões especificadas (OR).

```typescript
export const requireAnyPermission = (permissions: string[]) => {
  return async (req: Request, res: Response, next: NextFunction): Promise<void> => {
    // Verifica todas as permissões em paralelo
    // Verifica se pelo menos uma é verdadeira
    // Lança ForbiddenException se nenhuma for verdadeira
  };
};
```

**Características**:
- Verifica múltiplas permissões em paralelo (performance)
- Retorna true se pelo menos uma permissão for verdadeira
- Mensagem de erro lista todas as permissões necessárias

#### `requireAllPermissions(permissions: string[])`

Middleware factory que verifica se o usuário tem todas as permissões especificadas (AND).

```typescript
export const requireAllPermissions = (permissions: string[]) => {
  return async (req: Request, res: Response, next: NextFunction): Promise<void> => {
    // Verifica todas as permissões em paralelo
    // Verifica se todas são verdadeiras
    // Lança ForbiddenException se alguma for falsa
  };
};
```

**Características**:
- Verifica múltiplas permissões em paralelo (performance)
- Retorna true apenas se todas as permissões forem verdadeiras
- Mensagem de erro lista todas as permissões necessárias

## Exemplos de Uso

### Exemplo 1: Proteger rota com permissão

```typescript
import { Router } from 'express';
import { authMiddleware } from '../middleware/auth';
import { requirePermission } from '../middleware/authorization';
import { usuarioController } from '../controllers/UsuarioController';

const router = Router();

// Rota protegida: requer autenticação + permissão 'usuario.create'
router.post(
  '/usuarios',
  authMiddleware,              // 1. Verifica autenticação
  requirePermission('usuario.create'),  // 2. Verifica permissão
  usuarioController.create     // 3. Executa controller
);
```

### Exemplo 2: Proteger rota com role

```typescript
// Rota protegida: requer autenticação + role 'ADMIN'
router.delete(
  '/usuarios/:id',
  authMiddleware,
  requireRole('ADMIN'),
  usuarioController.delete
);
```

### Exemplo 3: Múltiplas roles (OR)

```typescript
// Rota protegida: requer autenticação + role 'ADMIN' OU 'MANAGER'
router.put(
  '/usuarios/:id',
  authMiddleware,
  requireRole(['ADMIN', 'MANAGER']),
  usuarioController.update
);
```

### Exemplo 4: Múltiplas permissões (OR)

```typescript
// Rota protegida: requer pelo menos uma das permissões
router.get(
  '/relatorios',
  authMiddleware,
  requireAnyPermission(['relatorio.financeiro', 'relatorio.geral']),
  relatorioController.list
);
```

### Exemplo 5: Múltiplas permissões (AND)

```typescript
// Rota protegida: requer todas as permissões
router.post(
  '/usuarios/admin',
  authMiddleware,
  requireAllPermissions(['usuario.create', 'usuario.admin']),
  usuarioController.createAdmin
);
```

### Exemplo 6: Combinando com validação

```typescript
import { validateDto } from '../middleware/validation';
import { CreateUsuarioDto } from '../application/dto/usuario';

router.post(
  '/usuarios',
  authMiddleware,                              // 1. Autenticação
  requirePermission('usuario.create'),         // 2. Autorização
  validateDto(CreateUsuarioDto),              // 3. Validação
  asyncHandler(async (req, res) => {           // 4. Controller
    await usuarioController.create(req, res);
  })
);
```

## Fluxo de Execução

### Fluxo Normal (com permissão/role)

```
1. Requisição HTTP chega
   ↓
2. authMiddleware verifica token e define req.userId
   ↓
3. requirePermission/requireRole verifica permissão/role
   ↓
4. AuthorizationService verifica no banco de dados
   ↓
5. Se tiver permissão/role → next() → Controller
   ↓
6. Controller executa e retorna resposta
```

### Fluxo de Erro (sem permissão/role)

```
1. Requisição HTTP chega
   ↓
2. authMiddleware verifica token e define req.userId
   ↓
3. requirePermission/requireRole verifica permissão/role
   ↓
4. AuthorizationService verifica no banco de dados
   ↓
5. Se NÃO tiver permissão/role → lança ForbiddenException
   ↓
6. errorHandler captura ForbiddenException
   ↓
7. Retorna resposta 403 com mensagem de erro
```

### Fluxo de Erro (não autenticado)

```
1. Requisição HTTP chega
   ↓
2. authMiddleware verifica token
   ↓
3. Se token inválido/ausente → retorna 401
   ↓
4. Se token válido mas requirePermission/requireRole não encontra req.userId
   → lança UnauthorizedException
   ↓
5. errorHandler captura UnauthorizedException
   ↓
6. Retorna resposta 401 com mensagem de erro
```

## Tratamento de Erros

O middleware utiliza o sistema de exceções centralizado, lançando exceções que são tratadas pelo `errorHandler`:

### Erro 401 (Não Autenticado)

Se `req.userId` não estiver definido, o middleware lança `UnauthorizedException`:

```typescript
throw new UnauthorizedException('Credenciais inválidas');
```

O `errorHandler` trata a exceção e retorna:

```json
{
  "success": false,
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Credenciais inválidas"
  },
  "timestamp": "2024-01-01T00:00:00.000Z",
  "path": "/api/usuarios",
  "requestId": "uuid-da-requisicao"
}
```

### Erro 403 (Sem Permissão/Role)

Se o usuário não tiver a permissão/role necessária, o middleware lança `ForbiddenException`:

```typescript
throw new ForbiddenException(`Permissão '${permission}' necessária`);
```

O `errorHandler` trata a exceção e retorna:

```json
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "Permissão 'usuario.create' necessária"
  },
  "timestamp": "2024-01-01T00:00:00.000Z",
  "path": "/api/usuarios",
  "requestId": "uuid-da-requisicao"
}
```

**Vantagens desta abordagem**:
- Consistência: Todas as exceções são tratadas pelo `errorHandler`
- Formatação padronizada: Respostas de erro seguem o mesmo formato
- Logging automático: O `errorHandler` registra todas as exceções
- Manutenibilidade: Mudanças no formato de erro são centralizadas

## Considerações de Performance

### Cache de Permissões

O middleware depende do `AuthorizationService` que pode implementar cache de permissões (T11.3). Isso é importante porque:

- O middleware é executado em **cada requisição** protegida
- Verificações de permissão podem ser frequentes
- Cache reduz carga no banco de dados

### Verificações em Paralelo

As funções `requireAnyPermission` e `requireAllPermissions` verificam múltiplas permissões em paralelo usando `Promise.all()`, melhorando a performance quando há múltiplas verificações.

## Segurança

### Validação de Autenticação

O middleware sempre verifica se `req.userId` está definido antes de verificar permissões. Isso garante que:

- Usuários não autenticados não podem acessar rotas protegidas
- O middleware não depende apenas do `authMiddleware` estar presente
- `UnauthorizedException` é lançada quando não há autenticação

### Tratamento de Erros

Erros são tratados adequadamente através do sistema de exceções centralizado:

- `UnauthorizedException` é lançada quando não há autenticação (401)
- `ForbiddenException` é lançada quando não há permissão/role (403)
- Todas as exceções são passadas para o `errorHandler` que formata a resposta
- Mensagens de erro não expõem informações sensíveis
- Logging automático de todas as exceções pelo `errorHandler`

---

## Limitações e Considerações

### Dependência de AuthorizationService

O middleware depende da implementação de `AuthorizationService` (T11.3). Se o serviço não estiver implementado, o middleware lançará erro ao tentar resolver do container.

**Solução**: Implementar `AuthorizationService` antes de usar o middleware em produção.

### Ordem de Middlewares

A ordem dos middlewares é crítica:

- `authMiddleware` deve vir **antes** do middleware de autorização
- `requestContextMiddleware` deve vir **antes** do `authMiddleware` (se usado)

### Performance

O middleware executa verificações de permissão em cada requisição. Para melhorar performance:

- Use cache de permissões no `AuthorizationService`
- Considere usar decorators em Application Services quando possível (mais eficiente)
