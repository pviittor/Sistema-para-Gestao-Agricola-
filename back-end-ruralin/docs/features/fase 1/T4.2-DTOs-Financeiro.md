## Implementação Detalhada

### Validador Customizado IsDateAfter

```typescript
@ValidatorConstraint({ async: false })
export class IsDateAfterConstraint implements ValidatorConstraintInterface {
  validate(value: any, args: ValidationArguments): boolean {
    const [compareDateProperty, allowEqual = true] = args.constraints;
    const object = args.object as any;
    
    const dateValue = value;
    const compareDate = object[compareDateProperty];
    
    if (!compareDate) {
      return true; // Deixar outras validações tratarem
    }
    
    const dateValueObj = new Date(dateValue);
    const compareDateObj = new Date(compareDate);
    
    // Normalizar para comparar apenas datas (sem hora)
    dateValueObj.setHours(0, 0, 0, 0);
    compareDateObj.setHours(0, 0, 0, 0);
    
    // Se allowEqual é true, permite datas iguais
    if (allowEqual) {
      return dateValueObj >= compareDateObj;
    }
    
    return dateValueObj > compareDateObj;
  }
}
```

**Uso**:
```typescript
@IsDateAfter('dataEmissao', true, { message: 'Data de vencimento deve ser posterior ou igual à data de emissão' })
dataVencimento!: string;
```

## Validador Customizado IsDateAfter

### Funcionamento

O validador `IsDateAfter` valida que uma data é posterior ou igual a outra:

1. **Comparação de Datas**: Compara apenas a parte de data (ignora hora)
2. **Permite Igualdade**: Por padrão, permite datas iguais (configurável)
3. **Validação Condicional**: Só valida se a data de comparação também for fornecida

### Implementação

```typescript
@IsDateAfter('dataEmissao', true, { message: 'Data de vencimento deve ser posterior ou igual à data de emissão' })
dataVencimento!: string;
```

**Parâmetros**:
- `compareDateProperty`: Nome da propriedade com data de comparação ('dataEmissao')
- `allowEqual`: Se true, permite datas iguais (padrão: true)
- `validationOptions`: Opções do class-validator

### Exemplo de Uso

```typescript
// CreateFinanceiroDto (permite datas iguais)
@IsDateAfter('dataEmissao', true, { message: 'Data de vencimento deve ser posterior ou igual à data de emissão' })
dataVencimento!: string;

// UpdateFinanceiroDto (validação condicional)
@ValidateIf((o) => o.dataVencimento !== undefined && o.dataEmissao !== undefined)
@Validate(IsDateAfter, ['dataEmissao'])
dataVencimento?: string;
```

## Valores Positivos e Negativos

### Receitas (Valores Positivos)

Valores positivos representam receitas/entradas de dinheiro:
- ✅ `1500.50` - Receita de R$ 1.500,50
- ✅ `0.01` - Receita mínima
- ✅ `999999.99` - Receita máxima

### Despesas (Valores Negativos)

Valores negativos representam despesas/saídas de dinheiro:
- ✅ `-500.00` - Despesa de R$ 500,00
- ✅ `-0.01` - Despesa mínima
- ✅ `-999999.99` - Despesa máxima

### Validação

O sistema aceita qualquer número válido (positivo ou negativo):
- Não há validação específica de tipo de transação
- A lógica de negócio pode determinar se é receita ou despesa baseado no valor
- Validação apenas garante que é um número válido

## Padrões de Formato

### Data

Formato: `YYYY-MM-DD`

**Exemplos**:
- ✅ `2025-01-20` - Válido
- ✅ `2025-12-31` - Válido
- ❌ `20-01-2025` - Inválido
- ❌ `2025/01/20` - Inválido
- ❌ `data-invalida` - Inválido

### Valor

Formato: Número (positivo ou negativo)

**Exemplos**:
- ✅ `1500.50` - Receita válida
- ✅ `-500.00` - Despesa válida
- ✅ `0` - Zero válido
- ❌ `"1500.50"` - String inválida
- ❌ `abc` - Não numérico

### Validação de Datas

- ✅ `dataVencimento` deve ser posterior ou igual a `dataEmissao`
- ✅ Em updates, validação só ocorre se ambas as datas forem fornecidas
- ✅ Datas iguais são permitidas por padrão

## Troubleshooting

### Problema: Validação de IsDateAfter não funciona em updates

**Sintomas**: Validação falha mesmo quando datas são válidas

**Solução**:
1. Verificar se está usando `@ValidateIf()` corretamente
2. Verificar se `dataEmissao` está sendo fornecida junto com `dataVencimento`
3. Verificar se o formato de data está correto (YYYY-MM-DD)

### Problema: Campos undefined causam erro no Sequelize

**Sintomas**: Erro ao criar/atualizar registro financeiro

**Solução**:
1. Filtrar campos undefined antes de passar para Sequelize
2. Usar verificação condicional (`if (campo !== undefined)`)
3. Não usar spread operator diretamente com DTOs que têm campos opcionais

### Problema: Data inválida passa na validação

**Sintomas**: Data em formato incorreto passa na validação

**Solução**:
1. Verificar se `@IsDateString()` está aplicado corretamente
2. Verificar se o formato está correto (YYYY-MM-DD)
3. Verificar se `transform: true` está habilitado no middleware
