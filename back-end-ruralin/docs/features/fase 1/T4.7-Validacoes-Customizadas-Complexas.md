## Validadores Implementados

### 1. IsUnique

**Propósito**: Valida se um valor é único em uma tabela do banco de dados.

**Características**:
- ✅ Validação assíncrona (consulta ao banco)
- ✅ Suporte para exclusão de registro atual em updates
- ✅ Mensagens de erro personalizadas

**Uso**:
```typescript
import { IsUnique } from '../../validators/IsUnique';

export class CreateUsuarioDto {
  // Para criação - verifica unicidade simples
  @IsUnique('Usuario', 'email', undefined, { message: 'Email já está em uso' })
  email!: string;

  // Para atualização - exclui o próprio registro
  @IsUnique('Usuario', 'email', 'id', { message: 'Email já está em uso' })
  email?: string;
}
```

**Parâmetros**:
- `modelName`: Nome do modelo Sequelize (ex: 'Usuario', 'Role')
- `columnName`: Nome da coluna a validar (ex: 'email', 'nome')
- `excludeId`: Campo ou valor para excluir da validação (útil para updates)
  - `undefined`: Não exclui nenhum registro (criação)
  - `'id'`: Exclui o registro com ID do objeto (atualização)
  - `number`: Exclui o registro com esse ID específico

**Casos de Uso**:
- ✅ Validação de email único
- ✅ Validação de username único
- ✅ Validação de nome de role único
- ✅ Validação de nome de permissão único

### 2. IsExists

**Propósito**: Valida se um valor (geralmente um ID) existe em uma tabela do banco de dados.

**Características**:
- ✅ Validação assíncrona (consulta ao banco)
- ✅ Validação de relacionamentos (foreign keys)
- ✅ Mensagens de erro contextuais

**Uso**:
```typescript
import { IsExists } from '../../validators/IsExists';

export class CreateEventoDto {
  @IsExists('Local', 'id', { message: 'Local não encontrado' })
  localId!: number;
}
```

**Parâmetros**:
- `modelName`: Nome do modelo Sequelize (ex: 'Local', 'Usuario')
- `columnName`: Nome da coluna a validar (geralmente 'id')

**Casos de Uso**:
- ✅ Validação de foreign keys
- ✅ Validação de relacionamentos obrigatórios
- ✅ Validação de referências válidas

### 3. IsDateAfter

**Propósito**: Valida que uma data é posterior ou igual a outra data.

**Características**:
- ✅ Validação síncrona (sem consulta ao banco)
- ✅ Suporte para permitir datas iguais
- ✅ Normalização de datas (sem hora)

**Uso**:
```typescript
import { IsDateAfter } from '../../validators/IsDateAfter';

export class CreateFinanceiroDto {
  @IsDateString({}, { message: 'Data de emissão deve ser uma data válida' })
  dataEmissao!: string;

  // Permite datas iguais (padrão)
  @IsDateAfter('dataEmissao', true, { 
    message: 'Data de vencimento deve ser posterior ou igual à data de emissão' 
  })
  dataVencimento!: string;

  // Não permite datas iguais
  @IsDateAfter('dataInicio', false, { 
    message: 'Data de fim deve ser posterior à data de início' 
  })
  dataFim!: string;
}
```

**Parâmetros**:
- `compareDateProperty`: Nome da propriedade que contém a data de comparação
- `allowEqual`: Se `true`, permite datas iguais (padrão: `true`)
- `validationOptions`: Opções de validação do class-validator

**Casos de Uso**:
- ✅ Validação de data de vencimento >= data de emissão
- ✅ Validação de data de fim > data de início
- ✅ Validação de períodos válidos

### 4. IsTimeAfter

**Propósito**: Valida que um horário de fim é posterior ao horário de início.

**Características**:
- ✅ Validação síncrona (sem consulta ao banco)
- ✅ Suporte para considerar data (eventos em dias diferentes)
- ✅ Tratamento especial para eventos históricos

**Uso**:
```typescript
import { IsTimeAfter } from '../../validators/IsTimeAfter';

export class CreateEventoDto {
  @Matches(/^([0-1][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]$/, {
    message: 'Horário de início deve estar no formato HH:mm:ss',
  })
  horario_inicio!: string;

  // Considera a data do evento para validação
  @IsTimeAfter('horario_inicio', 'data', { 
    message: 'Horário de fim deve ser posterior ao horário de início' 
  })
  horario_fim!: string;
}
```

**Parâmetros**:
- `startTimeProperty`: Nome da propriedade que contém o horário de início
- `dateProperty`: Nome da propriedade que contém a data (opcional)
- `validationOptions`: Opções de validação do class-validator

**Comportamento**:
- Se `dateProperty` for fornecido: Cria objetos Date completos para comparação
- Se `dateProperty` não for fornecido: Compara apenas os horários
- Eventos históricos (data no passado): Não valida (permite qualquer horário)

**Casos de Uso**:
- ✅ Validação de horário de fim > horário de início
- ✅ Validação de eventos com data e hora
- ✅ Validação de períodos de tempo válidos

### 5. IsValidEnum

**Propósito**: Valida se um valor pertence a um enum específico, com mensagens de erro personalizadas.

**Características**:
- ✅ Validação síncrona (sem consulta ao banco)
- ✅ Suporte para enums string e numéricos
- ✅ Mensagens de erro com valores válidos

**Uso**:
```typescript
import { IsValidEnum } from '../../validators/IsValidEnum';

enum UsuarioTipo {
  ROOT = 'ROOT',
  CLIENT = 'CLIENT'
}

export class CreateUsuarioDto {
  @IsValidEnum(UsuarioTipo, { message: 'Tipo deve ser ROOT ou CLIENT' })
  tipo!: UsuarioTipo;
}
```

**Parâmetros**:
- `enumObject`: Objeto enum a validar
- `validationOptions`: Opções de validação do class-validator

**Vantagens sobre `@IsEnum`**:
- ✅ Mensagens de erro mais descritivas
- ✅ Suporte para valores opcionais (deixa `@IsOptional` tratar)
- ✅ Melhor integração com o sistema de validação

**Casos de Uso**:
- ✅ Validação de tipos de usuário (ROOT/CLIENT)
- ✅ Validação de status (ACTIVE/INACTIVE/PENDING)
- ✅ Validação de prioridades (LOW/MEDIUM/HIGH)
- ✅ Validação de enums numéricos

### 6. IsRequiredIf

**Propósito**: Valida que um campo é obrigatório se outro campo tiver um valor específico.

**Características**:
- ✅ Validação síncrona (sem consulta ao banco)
- ✅ Validação condicional cross-field
- ✅ Mensagens de erro contextuais

**Uso**:
```typescript
import { IsRequiredIf } from '../../validators/IsRequiredIf';

enum TipoFinanceiro {
  RECEITA = 'RECEITA',
  DESPESA = 'DESPESA'
}

export class CreateFinanceiroDto {
  @IsValidEnum(TipoFinanceiro)
  tipo!: TipoFinanceiro;

  // Categoria é obrigatória apenas para despesas
  @IsRequiredIf('tipo', 'DESPESA', { 
    message: 'Categoria é obrigatória para despesas' 
  })
  categoriaId?: number;

  // Data de pagamento é obrigatória apenas se status for 'PAGO'
  @IsRequiredIf('status', 'PAGO', { 
    message: 'Data de pagamento é obrigatória quando status é PAGO' 
  })
  dataPagamento?: string;
}
```

**Parâmetros**:
- `conditionProperty`: Nome da propriedade que deve ser verificada
- `conditionValue`: Valor que a propriedade deve ter para tornar o campo obrigatório
- `validationOptions`: Opções de validação do class-validator

**Casos de Uso**:
- ✅ Campo obrigatório apenas em condições específicas
- ✅ Validações condicionais baseadas em outros campos
- ✅ Regras de negócio complexas

## Comparação: Validadores Customizados vs Padrão

### IsValidEnum vs IsEnum

**Antes (IsEnum padrão)**:
```typescript
@IsEnum(UsuarioTipo, { message: 'Tipo deve ser ROOT ou CLIENT' })
tipo!: UsuarioTipo;
```

**Depois (IsValidEnum customizado)**:
```typescript
@IsValidEnum(UsuarioTipo, { message: 'Tipo deve ser ROOT ou CLIENT' })
tipo!: UsuarioTipo;
```

**Vantagens**:
- ✅ Mensagens de erro mais descritivas (mostra valores válidos)
- ✅ Melhor tratamento de valores opcionais
- ✅ Consistência com outros validadores customizados

### Validações Cross-Field

**Antes (Validação manual no controller)**:
```typescript
async create(req: Request, res: Response) {
  const { dataEmissao, dataVencimento } = req.body;
  
  if (new Date(dataVencimento) < new Date(dataEmissao)) {
    return res.status(400).json({ 
      error: 'Data de vencimento deve ser posterior à data de emissão' 
    });
  }
  
  // ...
}
```

**Depois (Validação automática via DTO)**:
```typescript
export class CreateFinanceiroDto {
  @IsDateAfter('dataEmissao', true, { 
    message: 'Data de vencimento deve ser posterior ou igual à data de emissão' 
  })
  dataVencimento!: string;
}
```

**Vantagens**:
- ✅ Validação ocorre antes do controller
- ✅ Mensagens de erro padronizadas
- ✅ Código mais limpo e focado
- ✅ Reutilizável em múltiplos DTOs

## Padrões e Boas Práticas

### 1. Use Validadores Customizados para Regras de Negócio

```typescript

  message: 'Data de vencimento deve ser posterior ou igual à data de emissão' 
})

// ⚠️ Evitar - Validação simples pode usar validadores padrão

```


## Troubleshooting

### Problema: Validador assíncrono não está funcionando

**Sintomas**: Validação sempre retorna `true` ou não executa

**Solução**:
1. Verificar se `@ValidatorConstraint({ async: true })` está definido
2. Verificar se o método `validate` retorna `Promise<boolean>`
3. Verificar se o middleware de validação está configurado corretamente

### Problema: Validação cross-field não funciona

**Sintomas**: Validação não considera outros campos

**Solução**:
1. Verificar se os campos estão no mesmo DTO
2. Verificar se os nomes das propriedades estão corretos
3. Verificar se os campos estão sendo validados na ordem correta

### Problema: Mensagem de erro não aparece

**Sintomas**: Mensagem padrão aparece ao invés da customizada

**Solução**:
1. Verificar se `validationOptions.message` está definido
2. Verificar se `defaultMessage` está implementado corretamente
3. Verificar se o middleware de validação está usando as mensagens corretas
