## Decisões de Implementação

### Abordagem Escolhida

**Separação de Responsabilidades**:
- Controller: Apenas orquestração HTTP (request/response)
- Application Service: Lógica de negócio
- Repository: Acesso a dados

**Lógica de Relacionamentos**:
- Mantida temporariamente no controller (roles, subUsuarios)
- Marcada com TODO para futura refatoração
- Pode ser movida para o Application Service em iteração futura

**Validações**:
- Validações de DTOs continuam no middleware de validação
- Validações de negócio movidas para o Application Service
- Controller não faz validações

### 2. Método `create`

**Antes**:
```typescript
async create(req: Request, res: Response) {
  const dto = req.body as CreateUsuarioDto;
  const { senha, roleIds, ...rest } = dto;
  
  // Hash da senha no controller ❌
  const hashedPassword = await bcrypt.hash(senha, 8);
  usuarioData.senha = hashedPassword;

  // Criação direta no model ❌
  const usuario = await Usuario.create(usuarioData);
  
  // Lógica de relacionamentos no controller ❌
  if (roleIds && Array.isArray(roleIds)) {
    await Promise.all(roleIds.map(roleId => 
      UsuarioHasRole.create({...})
    ));
  }
  
  // Remoção manual de senha ❌
  const usuarioJson = usuario.toJSON();
  delete usuarioJson.senha;
  
  return res.status(201).json(usuarioJson);
}
```

**Depois**:
```typescript
async create(req: Request, res: Response) {
  const dto = req.body as CreateUsuarioDto;
  
  // Usar service para criar usuário ✅
  // Service aplica hash de senha e validações
  const usuario = await this.usuarioService.create(dto);
  
  // Lógica de relacionamentos mantida temporariamente
  // TODO: Mover para o Application Service
  const { roleIds } = dto;
  if (roleIds && Array.isArray(roleIds)) {
    await Promise.all(roleIds.map(roleId => 
      UsuarioHasRole.create({
        usuarioId: usuario.id,
        roleId
      })
    ));
  }
  
  return res.status(201).json(usuario);
}
```

**Benefícios**:
- ✅ Hash de senha movido para o mapper (via service)
- ✅ Validações de negócio no service
- ✅ Controller apenas orquestra HTTP
- ✅ Código mais limpo e focado

## Responsabilidades do Controller

### O que o Controller FAZ

1. **Recebe requisições HTTP**
   - Extrai dados de `req.body`, `req.params`, `req.query`
   - Tipa dados como DTOs

2. **Chama Application Service**
   - Delega toda lógica de negócio para o service
   - Não faz validações de negócio
   - Não acessa models diretamente

3. **Retorna respostas HTTP**
   - Define status codes apropriados
   - Retorna DTOs (já sem dados sensíveis)
   - Enriquece com relacionamentos (se necessário)

### O que o Controller NÃO FAZ

1. **Não faz validações de negócio**
   - Validações de DTOs: middleware de validação
   - Validações de negócio: Application Service

2. **Não acessa models diretamente**
   - Acesso a dados: Repository (via Application Service)

3. **Não aplica transformações de dados**
   - Hash de senha: Mapper (via Application Service)
   - Conversão DTO-Entidade: Mapper (via Application Service)

4. **Não contém lógica de negócio**
   - Regras de negócio: Application Service
   - Validações de unicidade: Application Service

## Padrões e Convenções

### Estrutura de Controller

```typescript
@Injectable()
export class UsuarioController implements IUsuarioController {
  constructor(
    @Inject(TYPES.IUsuarioApplicationService)
    private usuarioService: IUsuarioApplicationService
  ) {}

  async create(req: Request, res: Response) {
    // 1. Extrair DTO da requisição
    const dto = req.body as CreateUsuarioDto;
    
    // 2. Chamar Application Service
    const result = await this.usuarioService.create(dto);
    
    // 3. Retornar resposta HTTP
    return res.status(201).json(result);
  }
}
```

### Fluxo de Dados

```
HTTP Request
    ↓
Controller (extrai DTO)
    ↓
Application Service (lógica de negócio)
    ↓
Mapper (conversão DTO ↔ Entidade)
    ↓
Repository (acesso a dados)
    ↓
Database
```
