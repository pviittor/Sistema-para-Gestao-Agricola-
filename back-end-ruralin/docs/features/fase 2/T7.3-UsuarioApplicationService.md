## Decisões de Implementação

### Abordagem Escolhida

**Application Service Pattern**:
- Separa controllers (HTTP) da lógica de negócio
- Centraliza regras de negócio em um único lugar
- Facilita testes e manutenção
- Reutilizável em diferentes contextos (HTTP, CLI, etc.)

**Integração com Dependências**:
- Usa `IUsuarioRepository` para acesso a dados
- Usa `UsuarioMapper` para conversão DTO-Entidade
- Injeta dependências via DI container

**Validações de Negócio**:
- Verifica unicidade de email e username no `create`
- Verifica unicidade de email e username no `update` (se alterados)
- Lança exceções apropriadas (`BusinessException`, `NotFoundException`)

## Métodos Implementados

### `create(dto: CreateUsuarioDto): Promise<UsuarioResponseDto>`

Cria um novo usuário com validações de negócio.

**Implementação**:
```typescript
async create(dto: CreateUsuarioDto): Promise<UsuarioResponseDto> {
  // Validação: verificar se email já existe
  const existingByEmail = await this.repository.findByEmail(dto.email);
  if (existingByEmail) {
    throw new BusinessException('Email já está em uso');
  }

  // Validação: verificar se username já existe
  const existingByUsername = await this.repository.findByUsername(dto.username);
  if (existingByUsername) {
    throw new BusinessException('Username já está em uso');
  }

  // Converter DTO para entidade (mapper aplica hash de senha)
  const entity = await this.mapper.toEntity(dto);

  // Criar via repositório
  const created = await this.repository.create(entity as any);

  // Retornar como DTO
  return this.mapper.toDto(created);
}
```

**Validações**:
- ✅ Email único
- ✅ Username único
- ✅ Hash de senha aplicado pelo mapper

**Exemplo de Uso**:
```typescript

const usuario = await service.create({
  nome: 'João Silva',
  email: 'joao@example.com',

  // ...
```

### `update(id: number | string, dto: UpdateUsuarioDto): Promise<UsuarioResponseDto>`

Atualiza um usuário existente com validações.

**Implementação**:
```typescript
async update(id: number | string, dto: UpdateUsuarioDto): Promise<UsuarioResponseDto> {
  // Verificar se usuário existe
  const existing = await this.repository.findById(id);
  if (!existing) {
    throw new NotFoundException('Usuário', id);
  }

  // Validação: verificar se novo email já existe (se fornecido)
  if (dto.email && dto.email !== existing.email) {
    const emailExists = await this.repository.findByEmail(dto.email);
    if (emailExists) {
      throw new BusinessException('Email já está em uso');
    }
  }

  // Validação: verificar se novo username já existe (se fornecido)
  if (dto.username && dto.username !== existing.username) {
    const usernameExists = await this.repository.findByUsername(dto.username);
    if (usernameExists) {
      throw new BusinessException('Username já está em uso');
    }
  }

  // Converter DTO para entidade (mapper aplica hash de senha se fornecida)
  const entity = await this.mapper.toEntity(dto);

  // Atualizar via repositório
  const updated = await this.repository.update(id, entity as any);

  // Retornar como DTO
  return this.mapper.toDto(updated);
}
```

**Validações**:
- ✅ Usuário deve existir
- ✅ Novo email único (se alterado)
- ✅ Novo username único (se alterado)
- ✅ Hash de senha aplicado apenas se fornecida

**Exemplo de Uso**:
```typescript
const usuario = await service.update(1, {
  nome: 'João Silva Atualizado',
  email: 'novoemail@example.com',
});
```

## Validações de Negócio

### Regras Implementadas

1. **Email Único**:
   - Verificado no `create`
   - Verificado no `update` (se email alterado)
   - Lança `BusinessException` se violado

2. **Username Único**:
   - Verificado no `create`
   - Verificado no `update` (se username alterado)
   - Lança `BusinessException` se violado

3. **Usuário Deve Existir**:
   - Verificado no `update` e `delete`
   - Lança `NotFoundException` se não encontrado

### Exceções Utilizadas

- **`BusinessException`**: Para violações de regras de negócio (email/username duplicado)
- **`NotFoundException`**: Para recursos não encontrados (usuário não existe)

## Comparação: Antes vs Depois

### Antes (Lógica no Controller)

```typescript
@Injectable()
export class UsuarioController {
  constructor(
    @Inject(TYPES.IUsuarioRepository)
    private repository: IUsuarioRepository
  ) {}

  async create(req: Request, res: Response) {
    // Lógica de negócio no controller ❌
    const existing = await this.repository.findByEmail(req.body.email);
    if (existing) {
      return res.status(400).json({ error: 'Email já está em uso' });
    }
    
    const entity = await mapper.toEntity(req.body);
    const created = await this.repository.create(entity);
    const dto = mapper.toDto(created);
    
    return res.status(201).json(dto);
  }
}
```

**Problemas**:
- ❌ Lógica de negócio misturada com HTTP
- ❌ Difícil reutilizar em outros contextos
- ❌ Difícil testar isoladamente
- ❌ Controllers ficam grandes

### Depois (Com Application Service)

```typescript
@Injectable()
export class UsuarioController {
  constructor(
    @Inject(TYPES.IUsuarioApplicationService)
    private service: IUsuarioApplicationService
  ) {}

  async create(req: Request, res: Response) {
    // Controller apenas orquestra HTTP ✅
    const dto = req.body as CreateUsuarioDto;
    const usuario = await this.service.create(dto);
    return res.status(201).json(usuario);
  }
}
```

**Benefícios**:
- ✅ Controller focado em HTTP
- ✅ Lógica de negócio no service
- ✅ Fácil reutilizar service
- ✅ Fácil testar isoladamente
