# T15.4 - Cache em Application Services

## Resumo Executivo

Aplicação de decorators de cache (`@Cacheable` e `@CacheEvict`) em todos os Application Services para otimizar métodos de leitura e escrita. O cache é aplicado de forma declarativa, melhorando significativamente a performance sem alterar a lógica de negócio.

## Contexto Técnico

### Por que Cache em Application Services?

**Necessidades de negócio**:
- **Performance**: Métodos de leitura são muito frequentes
- **Latência**: Cache é muito mais rápido que queries
- **Escalabilidade**: Reduz carga no banco de dados
- **Transparência**: Funciona sem alterar lógica de negócio

**Vantagens**:
- ✅ Cache declarativo e simples
- ✅ Invalidação automática
- ✅ TTLs configuráveis
- ✅ Compatível com outros decorators

## Estratégia de Cache

### TTLs Configurados

**Dados que mudam pouco** (TTL: 1 hora = 3600s):
- `getById` - Dados individuais
- `findByNome` - Roles e Permissões (dados estáticos)
- `list` - Roles e Permissões (dados estáticos)

**Dados que mudam ocasionalmente** (TTL: 30 minutos = 1800s):
- `findByEmail` - Usuários
- `findByUsername` - Usuários

**Dados que mudam frequentemente** (TTL: 10 minutos = 600s):
- `findByLocal` - Eventos por local
- `findByUsuario` - Locais e Lembretes por usuário

**Dados que mudam muito frequentemente** (TTL: 5 minutos = 300s):
- `list` - Listagens paginadas (exceto Roles e Permissões)
- `findByData` - Eventos por período
- `findByPeriodo` - Financeiro por período
- `findByTipo` - Financeiro por tipo
- `findProximos` - Próximos lembretes

### Padrão de Keys

**Formato**: `{entity}:{method}:{args}`

**Exemplos**:
- `usuario:getById:1` - Usuário por ID
- `usuario:list:1:10` - Lista paginada (página 1, limite 10)
- `usuario:findByEmail:user@example.com` - Usuário por email
- `evento:findByLocal:5` - Eventos por local
- `evento:findByData:2025-01-01:2025-01-31` - Eventos por período

### Invalidação de Cache

**Operações de Escrita**:
- `create` - Invalida cache de listagem e métodos relacionados
- `update` - Invalida cache do registro específico, listagem e métodos relacionados
- `delete` - Invalida cache do registro específico, listagem e métodos relacionados

**Padrões de Invalidação**:
- `{entity}:getById:{id}` - Cache específico do registro
- `{entity}:list:*` - Todas as listagens paginadas
- `{entity}:findBy*:*` - Todos os métodos de busca relacionados

## Exemplos de Implementação

### Exemplo 1: UsuarioApplicationService

```typescript
@Injectable()
export class UsuarioApplicationService implements IUsuarioApplicationService {
  // Método de leitura com cache
  @RequirePermission('usuario.read')
  @Cacheable('usuario:getById:{0}', 3600) // TTL: 1 hora
  async getById(id: number | string): Promise<UsuarioResponseDto | null> {
    const entity = await this.repository.findById(id);
    return entity ? this.mapper.toDto(entity) : null;
  }

  // Listagem com cache (TTL menor)
  @RequirePermission('usuario.read')
  @Cacheable('usuario:list:{0}:{1}', 300) // TTL: 5 minutos
  async list(page: number = 1, limit: number = 10): Promise<PaginatedResult<UsuarioResponseDto>> {
    const result = await this.repository.findAllPaginated(page, limit);
    return {
      ...result,
      data: result.data.map(entity => this.mapper.toDto(entity)),
    };
  }

  // Método de escrita com invalidação
  @RequirePermission('usuario.create')
  @Auditable('Usuario')
  @CacheEvict('usuario:list:*', true) // Invalida todas as listagens
  async create(dto: CreateUsuarioDto): Promise<UsuarioResponseDto> {
    // ... lógica de criação
  }

  // Atualização com invalidação múltipla
  @RequirePermission('usuario.update')
  @Auditable('Usuario')
  @CacheEvict('usuario:getById:{0}') // Invalida cache do registro
  @CacheEvict('usuario:list:*', true) // Invalida todas as listagens
  @CacheEvict('usuario:findByEmail:*', true) // Invalida busca por email
  @CacheEvict('usuario:findByUsername:*', true) // Invalida busca por username
  async update(id: number | string, dto: UpdateUsuarioDto): Promise<UsuarioResponseDto> {
    // ... lógica de atualização
  }
}
```

### Exemplo 2: EventoApplicationService

```typescript
@Injectable()
export class EventoApplicationService implements IEventoApplicationService {
  // Busca por local com cache
  @RequirePermission('evento.read')
  @Cacheable('evento:findByLocal:{0}', 600) // TTL: 10 minutos
  async findByLocal(localId: number): Promise<EventoResponseDto[]> {
    const entities = await this.repository.findByLocal(localId);
    return entities.map(entity => this.mapper.toDto(entity));
  }

  // Busca por período com cache (TTL menor)
  @RequirePermission('evento.read')
  @Cacheable('evento:findByData:{0}:{1}', 300) // TTL: 5 minutos
  async findByData(dataInicio: Date | string, dataFim: Date | string): Promise<EventoResponseDto[]> {
    const entities = await this.repository.findByData(dataInicio, dataFim);
    return entities.map(entity => this.mapper.toDto(entity));
  }

  // Criação com invalidação completa
  @RequirePermission('evento.create')
  @Transactional()
  @Auditable('Evento')
  @CacheEvict('evento:list:*', true)
  @CacheEvict('evento:findByLocal:*', true)
  @CacheEvict('evento:findByData:*', true)
  async create(dto: CreateEventoDto): Promise<EventoResponseDto> {
    // ... lógica de criação
  }
}
```

## Ordem dos Decorators

A ordem dos decorators importa. Ordem recomendada:

1. **Autorização** (`@RequirePermission`, `@RequireRole`)
2. **Transação** (`@Transactional`)
3. **Auditoria** (`@Auditable`)
4. **Cache** (`@Cacheable`, `@CacheEvict`)

**Exemplo**:
```typescript
@RequirePermission('usuario.update')
@Transactional()
@Auditable('Usuario')
@CacheEvict('usuario:getById:{0}')
@CacheEvict('usuario:list:*', true)
async update(id: number | string, dto: UpdateUsuarioDto): Promise<UsuarioResponseDto> {
  // 1. Verifica permissão
  // 2. Inicia transação
  // 3. Captura estado antes (auditoria)
  // 4. Executa método
  // 5. Registra auditoria
  // 6. Invalida cache
  // 7. Commit transação
}
```

## Integração com Sistema Existente

### Compatibilidade

Os decorators de cache são totalmente compatíveis com:
- ✅ `@RequirePermission` - Autorização
- ✅ `@RequireRole` - Autorização por role
- ✅ `@Transactional` - Transações
- ✅ `@Auditable` - Auditoria
- ✅ Cache no Repository (T15.3) - Funciona em camadas diferentes

### Camadas de Cache

O sistema agora possui cache em duas camadas:

1. **Repository Layer** (T15.3):
   - Cache automático em `findById` e `findAllPaginated`
   - Invalidação automática em `create`, `update`, `delete`
   - Cache de entidades do banco

2. **Application Service Layer** (T15.4):
   - Cache declarativo com decorators
   - Cache de DTOs (dados transformados)
   - Invalidação mais granular

**Vantagem**: Cache em duas camadas aumenta ainda mais a performance, pois:
- Repository cache: evita queries ao banco
- Service cache: evita transformações e validações

## Performance

### Vantagens

- **Redução de Queries**: Menos acesso ao banco de dados
- **Redução de Transformações**: DTOs cacheados evitam mapeamento
- **Latência**: Cache é muito mais rápido
- **Throughput**: Suporta mais requisições simultâneas

### Métricas Esperadas

**getById**:
- **Sem cache**: ~20-80ms (query + transformação)
- **Com cache**: ~1-5ms (cache hit)
- **Melhoria**: 20-80x mais rápido

**list**:
- **Sem cache**: ~50-200ms (query + transformação)
- **Com cache**: ~1-5ms (cache hit)
- **Melhoria**: 50-200x mais rápido

### Considerações

- **TTL**: Configurar TTL apropriado baseado em frequência de mudança
- **Memória**: Monitorar uso de memória do cache
- **Hit Rate**: Monitorar taxa de acertos do cache
- **Invalidação**: Invalidação adequada garante consistência

## Considerações Importantes

### Boas Práticas

1. **TTL Apropriado**: Usar TTL baseado em frequência de mudança
2. **Invalidação Completa**: Invalidar todos os caches relacionados
3. **Keys Descritivas**: Usar keys claras e consistentes
4. **Monitoramento**: Monitorar hit rate e uso de memória

### TTL Recomendado

- **Dados estáticos** (Roles, Permissões): 1 hora (3600s)
- **Dados raramente mudam** (getById): 1 hora (3600s)
- **Dados ocasionalmente mudam** (findByEmail, findByUsuario): 10-30 minutos (600-1800s)
- **Dados frequentemente mudam** (list, findByData): 5 minutos (300s)

### Limitações

- **Cache de null**: Resultados `null` não são cacheados
- **Cache de listagem**: Apenas `list` é cacheado, não `findAll` (muito variável)
- **Transações**: Cache não considera transações (pode haver inconsistência temporária)
- **Multi-instância**: Cache compartilhado (Redis) necessário para múltiplas instâncias
