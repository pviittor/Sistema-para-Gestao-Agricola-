## Funcionalidades

### 1. Armazenamento de TenantId

O serviço armazena o `tenantId` atual por instância. Como cada requisição terá sua própria instância (via middleware T17.4), o tenantId é isolado por requisição.

**Uso**:
```typescript
const tenantService = container.resolve<ITenantService>(TYPES.ITenantService);
tenantService.setCurrentTenantId(1);
const tenantId = tenantService.getCurrentTenantId(); // 1
```

### 2. Validação de Tenant

A validação verifica:
1. Se o tenantId é válido (número positivo)
2. Se o tenant existe (há usuários com aquele tenantId)
3. Se o usuário autenticado pertence ao tenant (se houver usuário autenticado)

**Uso**:
```typescript
const isValid = await tenantService.validateTenant(1);
if (!isValid) {
  throw new ForbiddenException('Acesso negado ao tenant');
}
```

### 3. Integração com RequestContext

O serviço utiliza `RequestContext` para obter o `userId` do usuário autenticado, permitindo validar se o usuário tem acesso ao tenant.

**Dependências**:
- `ILogger`: Para logging de operações
- `RequestContext`: Para obter userId (opcional)

---

## Decisões de Design

### 1. Armazenamento por Instância

**Decisão**: Armazenar `tenantId` como propriedade da instância

**Razão**:
- Cada requisição terá sua própria instância (via middleware)
- Simples e eficiente
- Não requer gerenciamento de estado global

**Alternativa Considerada**: Usar `RequestContext` para armazenar tenantId
- Rejeitada: TenantService é específico para tenants, RequestContext é mais genérico

### 2. Validação de Existência

**Decisão**: Verificar se existe pelo menos um usuário com o tenantId

**Razão**:
- Simples e eficiente
- Não requer tabela separada de tenants
- Baseado na estrutura atual (usuários têm tenantId)

**Alternativa Considerada**: Tabela separada de tenants
- Rejeitada: Adiciona complexidade desnecessária inicialmente

### 3. Validação de Acesso

**Decisão**: Verificar se usuário autenticado pertence ao tenant

**Razão**:
- Garante isolamento de dados
- Previne acesso não autorizado
- Baseado no tenantId do usuário

### 4. Singleton vs. Transient

**Decisão**: Registrar como Singleton no DI

**Razão**:
- Middleware criará nova instância por requisição (T17.4)
- Singleton permite reutilização quando apropriado
- Flexível para diferentes cenários

## Uso do Serviço

### Exemplo Básico

```typescript
import { container } from '../core/di/container';
import { TYPES } from '../core/di/types';
import { ITenantService } from '../core/tenant/ITenantService';

// Resolver serviço
const tenantService = container.resolve<ITenantService>(TYPES.ITenantService);

// Definir tenant atual
tenantService.setCurrentTenantId(1);

// Obter tenant atual
const tenantId = tenantService.getCurrentTenantId();

// Validar tenant
const isValid = await tenantService.validateTenant(1);
```

### Exemplo com Validação

```typescript
// Em um middleware ou controller
const tenantId = req.headers['x-tenant-id'] as string;

if (tenantId) {
  const tenantIdNum = parseInt(tenantId, 10);
  
  // Validar tenant
  const isValid = await tenantService.validateTenant(tenantIdNum);
  if (!isValid) {
    throw new ForbiddenException('Acesso negado ao tenant');
  }
  
  // Definir tenant atual
  tenantService.setCurrentTenantId(tenantIdNum);
}
```

## Integração com Outros Componentes

### RequestContext

O `TenantService` utiliza `RequestContext` para obter o `userId` do usuário autenticado. Isso permite validar se o usuário tem acesso ao tenant.

**Fluxo**:
1. Middleware de autenticação define `userId` no `RequestContext`
2. Middleware de tenant (T17.4) define `tenantId` no `TenantService`
3. `TenantService` valida se `userId.tenantId === tenantId`

### Logger

O serviço utiliza `ILogger` para registrar operações importantes:
- Definição de tenantId
- Validações de tenant
- Erros e avisos

## Notas de Implementação

### Considerações

1. **Instância por Requisição**: O serviço será usado com uma nova instância por requisição via middleware (T17.4)
2. **Validação de Acesso**: A validação verifica tanto existência quanto acesso do usuário
3. **Logging**: Todas as operações importantes são logadas para auditoria
4. **Tratamento de Erros**: Erros são tratados e retornam `false` em validações

### Limitações Atuais

1. **Sem Cache**: Validações fazem queries ao banco a cada chamada (pode ser otimizado depois)
2. **Sem Tabela de Tenants**: Validação baseada em usuários (pode ser melhorado depois)
3. **Sem Suporte a Multi-Tenant por Header**: Middleware será implementado em T17.4
