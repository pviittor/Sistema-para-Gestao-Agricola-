## Contexto Técnico

### Estado Atual

**Sistema Atual**:
- Tipos de usuário: `ROOT` e `CLIENT`
- Relacionamento: `UsuarioHasSubUsuario` (ROOT -> CLIENT)
- **Sem isolamento completo**: Dados não estão isolados por tenant
- **Sem campo tenantId**: Nenhuma tabela possui campo `tenantId`

**Problema**:
- Usuários CLIENT podem acessar dados de outros CLIENTs
- Não há isolamento de dados entre diferentes organizações
- Sistema não suporta múltiplos tenants de forma segura

**Solução Proposta**:
- Adicionar campo `tenantId` em todas as tabelas
- Migrar dados existentes atribuindo tenants apropriados
- Implementar isolamento completo de dados

## Mapeamento de Dados para Tenants

### Estratégia de Atribuição de Tenants

#### 1. Usuários ROOT
**Estratégia**: Cada usuário ROOT será um tenant próprio

**Lógica**:
- Cada `Usuario` com `tipo = 'ROOT'` recebe `tenantId = id` (próprio ID)
- Usuários ROOT são "donos" de seus próprios tenants

**Exemplo**:
```
Usuario ROOT (id=1) -> tenantId = 1
Usuario ROOT (id=5) -> tenantId = 5
```

#### 2. Usuários CLIENT
**Estratégia**: Herdam tenant do usuário ROOT relacionado

**Lógica**:
- Buscar relacionamento em `usuario_has_subUsuario`
- `subUsuarioId` (CLIENT) herda `tenantId` do `usuarioId` (ROOT)
- Se CLIENT não tiver ROOT relacionado, criar tenant próprio

**Exemplo**:
```
Usuario ROOT (id=1) -> tenantId = 1
Usuario CLIENT (id=2) relacionado a ROOT (id=1) -> tenantId = 1
Usuario CLIENT (id=3) relacionado a ROOT (id=1) -> tenantId = 1
```

#### 3. Dados Relacionados a Usuários
**Estratégia**: Herdam tenant do usuário proprietário

**Tabelas**:
- `eventos`: Herda `tenantId` de `usuarioId`
- `locais`: Herda `tenantId` de `usuarioId`
- `lembretes`: Herda `tenantId` de `usuarioId`
- `financeiros`: Herda `tenantId` de `usuarioId`
- `audit_logs`: Herda `tenantId` de `userId`

**Lógica**:
```sql
UPDATE eventos e
SET tenantId = (SELECT tenantId FROM usuarios WHERE id = e.usuarioId)
```

#### 4. Dados Relacionados Indiretamente
**Estratégia**: Herdam tenant através de relacionamentos

**Tabelas**:
- `lembrete_data_hora`: Herda `tenantId` de `lembreteId` -> `usuarioId`
- `eventos`: Já tem `usuarioId`, mas também pode herdar de `localId` -> `usuarioId` (validação)

**Lógica**:
```sql
UPDATE lembrete_data_hora ldh
SET tenantId = (
  SELECT u.tenantId 
  FROM lembretes l
  JOIN usuarios u ON u.id = l.usuarioId
  WHERE l.id = ldh.lembreteId
)
```

#### 5. Dados Globais (Roles e Permissões)
**Estratégia**: Duas opções

**Opção A - Compartilhados** (Recomendado):
- `roles` e `permissoes` não têm `tenantId` (NULL)
- Compartilhados entre todos os tenants
- Mais simples, menos isolamento

**Opção B - Isolados**:
- `roles` e `permissoes` têm `tenantId`
- Cada tenant tem seus próprios roles/permissões
- Mais isolamento, mais complexo

**Recomendação**: Opção A (compartilhados) inicialmente, migrar para Opção B se necessário.

#### 6. Tabelas de Junção
**Estratégia**: Herdam tenant das entidades relacionadas

**Tabelas**:
- `usuario_has_role`: Herda `tenantId` de `usuarioId`
- `role_has_permissao`: Não tem `tenantId` (se roles forem compartilhados) ou herda de `roleId`

## Plano de Rollback

### Cenários de Rollback

#### Cenário 1: Rollback Completo (Antes de NOT NULL)

**Condições**:
- Migração falhou antes de tornar tenantId NOT NULL
- Dados ainda podem ter tenantId NULL

**Ações**:
```sql
-- Remover colunas tenantId
ALTER TABLE usuarios DROP COLUMN tenantId;
ALTER TABLE eventos DROP COLUMN tenantId;
ALTER TABLE locais DROP COLUMN tenantId;
ALTER TABLE lembretes DROP COLUMN tenantId;

-- Se roles/permissoes foram alterados
ALTER TABLE roles DROP COLUMN tenantId;
ALTER TABLE permissoes DROP COLUMN tenantId;
ALTER TABLE role_has_permissao DROP COLUMN tenantId;
```

#### Cenário 2: Rollback Parcial (Após NOT NULL)

**Condições**:
- Migração falhou após tornar tenantId NOT NULL
- Dados já têm tenantId preenchido

**Ações**:
```sql
-- Tornar tenantId NULL novamente
ALTER TABLE usuarios MODIFY COLUMN tenantId INT NULL;
ALTER TABLE eventos MODIFY COLUMN tenantId INT NULL;
-- ... outras tabelas

-- Limpar tenantId
UPDATE usuarios SET tenantId = NULL;
UPDATE eventos SET tenantId = NULL;
-- ... outras tabelas

-- Remover colunas (se necessário)
-- (mesmo processo do Cenário 1)
```

#### Cenário 3: Restauração de Backup

**Condições**:
- Migração falhou completamente
- Dados corrompidos

**Ações**:
```bash
# Restaurar backup completo
mysql -u user -p database < backup_pre_migration.sql
```

## Estratégia de Atribuição de Tenants

### Regras de Negócio

#### 1. Usuários ROOT
- Cada ROOT é um tenant próprio
- `tenantId = id` (próprio ID)

#### 2. Usuários CLIENT
- CLIENT herda tenant do ROOT relacionado
- Se não tiver ROOT, recebe tenant próprio

#### 3. Dados de Usuários
- Herdam tenant do usuário proprietário
- `eventos`, `locais`, `lembretes`, `financeiros` → `usuarioId.tenantId`

#### 4. Dados Relacionados
- Herdam tenant através de relacionamentos
- `lembrete_data_hora` → `lembrete.usuarioId.tenantId`
- `eventos` → validação com `local.usuarioId.tenantId`

#### 5. Dados Globais
- `roles` e `permissoes`: Compartilhados (tenantId = NULL) ou isolados
- Recomendação: Compartilhados inicialmente

## Riscos e Mitigações

### Riscos Identificados

#### 1. CLIENTs sem ROOT relacionado
**Risco**: CLIENT sem ROOT não terá tenantId atribuído  
**Mitigação**: Atribuir tenantId próprio (id) para CLIENTs órfãos

#### 2. Inconsistência de tenantId em relacionamentos
**Risco**: Evento pode referenciar Local de outro tenant  
**Mitigação**: Validações pós-migração e constraints de aplicação

#### 3. Perda de dados durante migração
**Risco**: Erro durante migração pode corromper dados  
**Mitigação**: Backup completo antes de iniciar

#### 4. Performance durante migração
**Risco**: Migração pode ser lenta em grandes volumes  
**Mitigação**: Executar em horário de baixo tráfego, usar transações

#### 5. Downtime
**Risco**: Migração pode exigir downtime  
**Mitigação**: Executar em janela de manutenção, usar transações
