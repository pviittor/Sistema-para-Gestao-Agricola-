## Implementação

### 1. Migrations Criadas

#### 1.1. Migration 3: Popular tenantId em usuarios

**Arquivo**: `src/migrations/20240101000003-populate-tenantId-usuarios.ts`

**Lógica de Atribuição**:

1. **ROOTs**: `tenantId = id` (cada ROOT é seu próprio tenant)
2. **CLIENTs**: `tenantId = tenantId do ROOT relacionado` (via `usuario_has_subUsuario`)
3. **CLIENTs sem ROOT**: `tenantId = id` (fallback)

**Código Principal**:
```typescript
// Passo 1: ROOTs recebem tenantId = id
await queryInterface.sequelize.query(`
  UPDATE usuarios
  SET tenantId = id
  WHERE tipo = 'ROOT'
  AND tenantId IS NULL;
`);

// Passo 2: CLIENTs herdam tenantId do ROOT relacionado
await queryInterface.sequelize.query(`
  UPDATE usuarios u
  SET u.tenantId = (
    SELECT u2.tenantId
    FROM usuario_has_subUsuario uhs
    JOIN usuarios u2 ON u2.id = uhs.usuarioId
    WHERE uhs.subUsuarioId = u.id
    AND u2.tipo = 'ROOT'
    LIMIT 1
  )
  WHERE u.tipo = 'CLIENT'
  AND u.tenantId IS NULL
  AND EXISTS (...);
`);

// Passo 3: CLIENTs sem ROOT recebem tenantId = id (fallback)
await queryInterface.sequelize.query(`
  UPDATE usuarios
  SET tenantId = id
  WHERE tipo = 'CLIENT'
  AND tenantId IS NULL;
`);
```

**Validações**:
- Valida que todos os ROOTs têm `tenantId = id`
- Valida que todos os usuarios têm tenantId preenchido

#### 1.2. Migration 4: Popular tenantId em tabelas dependentes

**Arquivo**: `src/migrations/20240101000004-populate-tenantId-dependent-tables.ts`

**Lógica de Atribuição**:

- **eventos**: `tenantId` do `usuarioId`
- **locais**: `tenantId` do `usuarioId`
- **lembretes**: `tenantId` do `usuarioId`
- **financeiros**: `tenantId` do `usuarioId`
- **audit_logs**: `tenantId` do `userId` (se não for NULL)
- **lembrete_data_hora**: `tenantId` do `lembreteId` (via lembretes)
- **usuario_has_role**: `tenantId` do `usuarioId`

**Código Principal**:
```typescript
// eventos: tenantId do usuarioId
await queryInterface.sequelize.query(`
  UPDATE eventos e
  SET e.tenantId = (
    SELECT u.tenantId
    FROM usuarios u
    WHERE u.id = e.usuarioId
    LIMIT 1
  )
  WHERE e.tenantId IS NULL;
`);

// Similar para outras tabelas...
```

**Validações**:
- Valida que todas as tabelas têm tenantId preenchido
- Lança erro se encontrar registros sem tenantId

#### 1.3. Migration 5: Tornar tenantId NOT NULL

**Arquivo**: `src/migrations/20240101000005-make-tenantId-not-null.ts`

**Funcionalidade**:
- Valida que todas as tabelas têm tenantId preenchido
- Altera colunas tenantId para NOT NULL

**Código Principal**:
```typescript
// Validar antes de tornar NOT NULL
for (const table of tables) {
  const [result] = await queryInterface.sequelize.query(`
    SELECT COUNT(*) as sem_tenantId
    FROM ${table}
    WHERE tenantId IS NULL;
  `);

  if (result[0].sem_tenantId > 0) {
    throw new Error(`Falha na validação: ${result[0].sem_tenantId} registros sem tenantId na tabela ${table}`);
  }
}

// Tornar NOT NULL
await queryInterface.changeColumn('usuarios', 'tenantId', {
  type: DataTypes.INTEGER,
  allowNull: false,
  comment: 'ID do tenant ao qual o usuário pertence',
});
```

#### 1.4. Migration 6: Validar consistência de tenantId

**Arquivo**: `src/migrations/20240101000006-validate-tenant-consistency.ts`

**Validações de Consistência**:

1. **eventos → usuarios**: `eventos.tenantId = usuarios.tenantId`
2. **eventos → locais**: `eventos.tenantId = locais.tenantId`
3. **locais → usuarios**: `locais.tenantId = usuarios.tenantId`
4. **lembretes → usuarios**: `lembretes.tenantId = usuarios.tenantId`
5. **financeiros → usuarios**: `financeiros.tenantId = usuarios.tenantId`
6. **lembrete_data_hora → lembretes**: `lembrete_data_hora.tenantId = lembretes.tenantId`
7. **usuario_has_role → usuarios**: `usuario_has_role.tenantId = usuarios.tenantId`
8. **audit_logs → usuarios**: `audit_logs.tenantId = usuarios.tenantId` (se userId não for NULL)

**Código Principal**:
```typescript
// Validar consistência eventos -> usuarios
const [eventosUsuarios] = await queryInterface.sequelize.query(`
  SELECT COUNT(*) as inconsistencias
  FROM eventos e
  JOIN usuarios u ON u.id = e.usuarioId
  WHERE e.tenantId != u.tenantId;
`);

if (eventosUsuarios[0].inconsistencias > 0) {
  throw new Error(`Inconsistência encontrada: ${eventosUsuarios[0].inconsistencias} eventos com tenantId diferente do usuario`);
}
```

## Estratégia de Atribuição de TenantId

### 1. Usuarios

#### ROOTs
- **Regra**: `tenantId = id`
- **Razão**: Cada ROOT é seu próprio tenant
- **Exemplo**: Usuario ROOT com `id = 1` → `tenantId = 1`

#### CLIENTs
- **Regra**: `tenantId = tenantId do ROOT relacionado`
- **Razão**: CLIENTs pertencem ao tenant do ROOT que os gerencia
- **Fallback**: Se não tiver ROOT relacionado, `tenantId = id`
- **Exemplo**: CLIENT relacionado ao ROOT com `tenantId = 1` → `tenantId = 1`

### 2. Tabelas Dependentes

#### Baseado em usuarioId
- **eventos**: `tenantId` do `usuarioId`
- **locais**: `tenantId` do `usuarioId`
- **lembretes**: `tenantId` do `usuarioId`
- **financeiros**: `tenantId` do `usuarioId`
- **usuario_has_role**: `tenantId` do `usuarioId`
- **audit_logs**: `tenantId` do `userId` (se não for NULL)

#### Baseado em relacionamento indireto
- **lembrete_data_hora**: `tenantId` do `lembreteId` (via lembretes)

## Validações

### 1. Validações de Preenchimento

**Verifica**:
- Todos os registros têm tenantId preenchido
- Nenhum registro com tenantId NULL

**Query**:
```sql
SELECT COUNT(*) as sem_tenantId
FROM [tabela]
WHERE tenantId IS NULL;
-- Deve retornar 0
```

### 2. Validações de Consistência

**Verifica**:
- tenantId de entidades relacionadas são iguais
- Relacionamentos mantêm consistência de tenant

**Query**:
```sql
SELECT COUNT(*) as inconsistencias
FROM eventos e
JOIN usuarios u ON u.id = e.usuarioId
WHERE e.tenantId != u.tenantId;
-- Deve retornar 0
```

### 3. Validações de Regras Específicas

**ROOTs**:
```sql
SELECT COUNT(*) as total
FROM usuarios
WHERE tipo = 'ROOT'
AND (tenantId IS NULL OR tenantId != id);
-- Deve retornar 0
```

**CLIENTs**:
```sql
SELECT COUNT(*) as total
FROM usuarios u
WHERE u.tipo = 'CLIENT'
AND NOT EXISTS (
  SELECT 1
  FROM usuario_has_subUsuario uhs
  JOIN usuarios u2 ON u2.id = uhs.usuarioId
  WHERE uhs.subUsuarioId = u.id
  AND u2.tipo = 'ROOT'
  AND u.tenantId = u2.tenantId
)
AND u.tenantId != u.id;
-- Pode retornar > 0 (CLIENTs sem ROOT)
```

## Decisões de Design

### 1. Estratégia de Atribuição

**Decisão**: ROOTs recebem `tenantId = id`, CLIENTs herdam do ROOT

**Razão**:
- Simples e direto
- Cada ROOT é um tenant independente
- CLIENTs pertencem ao tenant do ROOT

**Alternativa Considerada**: Todos recebem `tenantId = id`
- Rejeitada: Não reflete relacionamento ROOT-CLIENT

### 2. Validações em Cada Migration

**Decisão**: Validar após cada passo da migração

**Razão**:
- Detecta problemas imediatamente
- Facilita debugging
- Previne propagação de erros

**Alternativa Considerada**: Validar apenas no final
- Rejeitada: Mais difícil identificar origem do problema

### 3. Migration de Validação Separada

**Decisão**: Criar migration separada apenas para validação

**Razão**:
- Pode ser executada independentemente
- Não modifica dados
- Pode ser re-executada sem problemas

**Alternativa Considerada**: Validações dentro das migrations de dados
- Rejeitada: Menos flexível, não pode ser re-executada facilmente

## Notas de Implementação

### Considerações

1. **Transações**: Migrations usam queries SQL diretas (não Sequelize ORM) para melhor performance
2. **Validações**: Validações em cada passo garantem integridade
3. **Rollback**: Cada migration tem método `down()` para rollback
4. **Idempotência**: Migrations podem ser re-executadas (com validações)

### Limitações Atuais

1. **Performance**: Migrations podem ser lentas em bancos grandes
2. **Lock de Tabelas**: UPDATEs podem bloquear tabelas durante migração
3. **Sem Progresso**: Não há indicador de progresso para migrations longas

### Melhorias Futuras

1. **Progresso**: Adicionar indicador de progresso
2. **Batch Processing**: Processar em lotes para melhor performance
3. **Paralelização**: Processar tabelas em paralelo (se possível)
