## Objetivos

- Garantir isolamento completo de dados entre tenants
- Implementar controle de acesso e desativação de tenants

---

## Contexto Técnico

### Estado Atual

**Sistema Atual**:
- Multi-tenancy básico implementado (T18.1 - T18.4)
- Tipos de usuário: `ROOT` e `CLIENT`
- Isolamento de dados por `tenantId`
- Sem hierarquia de consultorias
- Sem controle de ativação/desativação de tenants

**Problema**:
- Não há gerenciamento de múltiplas organizações (consultorias)
- Não há controle de acesso hierárquico
- Não há capacidade de desativar tenants sem perder dados
- Sistema não suporta distribuição WhiteLabel

**Solução Proposta**:
- Implementar hierarquia: GOD → CONSULTOR → TENANT
- Criar entidade `Consultoria` para agrupar tenants
- Adicionar controle de ativação/desativação
- Implementar validações de acesso hierárquico

## Princípios Arquiteturais

### 1. Isolamento Total de Dados

- Cada tenant possui isolamento completo
- Filtros automáticos por `tenantId` em todas as queries
- Validação cross-tenant em todas as operações
- BaseRepository aplica filtro automaticamente

### 2. Hierarquia de Acesso

- **GOD**: Acesso total, sem restrições, bypass de permissões
- **CONSULTOR**: Acesso apenas aos tenants da sua consultoria
- **ROOT/CLIENT**: Acesso apenas ao seu tenant

### 3. Controle de Ativação/Desativação

- Tenants podem ser desativados sem perder dados
- Desativação bloqueia acesso imediato (middleware)
- Reativação restaura acesso
- Consultorias também podem ser desativadas (cascade)

### 4. Multi-tenancy com Consultoria

- Consultorias são entidades de nível superior
- Tenants pertencem a uma consultoria
- Consultores gerenciam apenas seus tenants
- Isolamento por `consultoriaId` para consultores

## Fluxos Principais

### Autenticação

1. Usuário faz login
2. Valida credenciais
3. Verifica tipo de usuário (GOD/CONSULTOR/ROOT/CLIENT)
4. Verifica se tenant está ativo (se aplicável)
5. Verifica se consultoria está ativa (se aplicável)
6. Gera token JWT com `userId`, `tipo`, `tenantId`, `consultoriaId`
7. Retorna token e informações

### Criação de Consultoria (GOD)

1. GOD faz POST `/api/consultorias`
2. Valida permissão (apenas GOD)
3. Valida CNPJ único
4. Cria Consultoria com `ativo: true`
5. Retorna ConsultoriaResponseDto

### Criação de Tenant (CONSULTOR)

1. CONSULTOR faz POST `/api/tenants`
2. Valida permissão (apenas CONSULTOR)
3. Valida consultoria ativa
4. Valida limite de tenants
5. Valida slug único
6. Cria Tenant com `consultoriaId` e `ativo: true`
7. Incrementa `tenantCount` na Consultoria
8. Retorna TenantResponseDto

### Desativação de Tenant

1. CONSULTOR faz PUT `/api/tenants/:id/desativar`
2. Valida que tenant pertence à consultoria do CONSULTOR
3. Atualiza `ativo: false` e `dataDesativacao`
4. Middleware bloqueia acesso imediato
5. Retorna sucesso

## Edge Cases Identificados

1. **Desativação com usuários ativos**: Middleware verifica a cada request
2. **Limite de tenants excedido**: Validação no service, erro 400
3. **Desativação de consultoria**: Cascade para todos os tenants
4. **Migração de tenant**: Apenas GOD, operação crítica
5. **Conflito de slug**: Validação de unicidade global
6. **CONSULTOR sem consultoria**: Validação obrigatória
7. **Acesso de GOD**: Endpoint administrativo especial
8. **Reativação**: Valida consultoria ativa
9. **Expiração de limite**: GOD pode aumentar

## Riscos e Mitigações

### Riscos Técnicos

- **Isolamento de dados**: Filtros automáticos, testes, code review
- **Performance**: Índices, cache, monitoramento
- **Complexidade de queries**: Otimização, índices compostos
- **Transações cross-tenant**: Evitar, validação explícita se necessário

### Riscos de Segurança

- **Elevação de privilégios**: Validação no token JWT, server-side
- **Token comprometido**: Expiração curta, refresh tokens, blacklist
- **SQL Injection**: ORM com prepared statements, validação

### Riscos Operacionais

- **Migração de dados**: Incremental, rollback plan, testes
- **Downtime**: Deploy gradual, feature flags
