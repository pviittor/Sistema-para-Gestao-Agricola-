## Funcionalidades

### 1. Desativar Tenant (CONSULTOR)

**Endpoint**: `PUT /api/tenants/:id/desativar`

**Validações**:
- Apenas CONSULTOR pode desativar
- Tenant deve pertencer à consultoria do CONSULTOR
- Tenant deve estar ativo

**Lógica**:
1. Validar permissão (CONSULTOR)
2. Validar que tenant pertence à consultoria do CONSULTOR
3. Verificar se tenant está ativo
4. Atualizar `ativo: false`
5. Definir `dataDesativacao: now()`
6. Invalidar tokens JWT do tenant (opcional, fase futura)
7. Retornar sucesso

**Resposta**:
```json
{
  "success": true,
  "message": "Tenant desativado com sucesso",
  "data": {
    "id": 1,
    "ativo": false,
    "dataDesativacao": "2026-01-17T10:00:00Z"
  }
}
```

### 2. Ativar Tenant (CONSULTOR)

**Endpoint**: `PUT /api/tenants/:id/ativar`

**Validações**:
- Apenas CONSULTOR pode ativar
- Tenant deve pertencer à consultoria do CONSULTOR
- Tenant deve estar inativo
- Consultoria deve estar ativa

**Lógica**:
1. Validar permissão (CONSULTOR)
2. Validar que tenant pertence à consultoria do CONSULTOR
3. Verificar se tenant está inativo
4. Verificar se consultoria está ativa
5. Atualizar `ativo: true`
6. Definir `dataAtivacao: now()`
7. Limpar `dataDesativacao: null`
8. Retornar sucesso

**Resposta**:
```json
{

  "message": "Tenant ativado com sucesso",
  "data": {
    "id": 1,
    "ativo": true,
    "dataAtivacao": "2026-01-17T10:00:00Z"
```

## Middleware de Ativação

### tenantActivationMiddleware

**Localização**: `src/middleware/tenantActivation.ts`

**Responsabilidades**:
- Verificar se tenant está ativo (se aplicável)
- Verificar se consultoria está ativa (se aplicável)
- Bloquear acesso se inativo
- Retornar 403 Forbidden com mensagem clara

**Lógica**:
```typescript
1. Verificar se usuário tem tenantId (ROOT/CLIENT)
2. Se sim:
   a. Buscar tenant do banco
   b. Verificar se tenant está ativo
   c. Se inativo: retornar 403
   d. Verificar se consultoria está ativa
   e. Se inativa: retornar 403
3. Se usuário é CONSULTOR:
   a. Verificar se consultoria está ativa
   b. Se inativa: retornar 403
4. Continuar para próximo middleware
```

**Ordem de Execução**:
1. `requestContextMiddleware`
2. `authMiddleware`
3. `tenantActivationMiddleware` ← **NOVO**
4. `tenantMiddleware`
5. `authorizationMiddleware`

**Resposta de Erro**:
```json
{
  "success": false,
  "error": {
    "code": "TENANT_INACTIVE",
    "message": "O tenant está inativo e não pode acessar o sistema",
    "details": {
      "tenantId": 1,
      "dataDesativacao": "2026-01-17T10:00:00Z"
    }
  }
}
```

## Integração com AuthMiddleware

### Atualização do authMiddleware

**Arquivo**: `src/middleware/auth.ts`

**Alterações**:
1. Após validar token JWT, verificar tipo de usuário
2. Se ROOT/CLIENT, verificar se tenant está ativo
3. Se CONSULTOR, verificar se consultoria está ativa
4. Se GOD, não verificar (bypass)

**Lógica**:
```typescript
// Após validar token
if (user.tipo === 'ROOT' || user.tipo === 'CLIENT') {
  // Verificar tenant ativo (será feito pelo tenantActivationMiddleware)
  // Mas também pode ser verificado aqui para resposta mais rápida
}

if (user.tipo === 'CONSULTOR') {
  // Verificar consultoria ativa
  const consultoria = await Consultoria.findByPk(user.consultoriaId);
  if (!consultoria || !consultoria.ativo) {
    throw new ForbiddenException('Consultoria inativa');
  }
}
```

## Regras de Negócio

### 1. Desativação

- Apenas CONSULTOR pode desativar seus tenants
- Desativação é imediata (soft delete)
- Dados são mantidos no banco
- Acesso é bloqueado imediatamente via middleware
- Tokens JWT não são invalidados (validação a cada request)

### 2. Ativação

- Apenas CONSULTOR pode ativar seus tenants
- Consultoria deve estar ativa para reativar tenant
- Reativação restaura acesso imediato
- `dataAtivacao` é atualizada

### 3. Cascade de Desativação

- Se consultoria é desativada, todos os tenants são desativados
- Se tenant é desativado, usuários perdem acesso imediato
- Dados permanecem intactos

### 4. Validação em Cada Request

- Middleware verifica status a cada requisição
- Não confiar apenas no token JWT
- Verificação no banco de dados (com cache)

## Edge Cases

### 1. Desativação com Usuários Ativos

**Cenário**: CONSULTOR desativa tenant enquanto há usuários logados.

**Solução**:
- Middleware verifica status a cada request
- Usuários recebem 403 na próxima requisição
- Não há necessidade de invalidar tokens (validação dinâmica)

### 2. Reativação Imediata

**Cenário**: CONSULTOR reativa tenant logo após desativar.

**Solução**:
- Cache é invalidado imediatamente
- Próxima requisição já permite acesso
- `dataAtivacao` é atualizada

### 3. Consultoria Desativada

**Cenário**: Consultoria é desativada, mas tenant ainda está ativo.

**Solução**:
- Middleware verifica ambos (tenant e consultoria)
- Se consultoria inativa, bloqueia acesso mesmo se tenant ativo
- Cascade desativa todos os tenants
